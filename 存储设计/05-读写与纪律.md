# 05 · 玛丽读写存储

> **本篇修正了上一版设计的一处重大误读。** 上一版把 marie 文档里一句"玛丽不直连存储"放大成了一套架构契约（冻结接口、两个实现、可替换性判据）。那是误读。

---

## 一、先纠正那个误读

marie 文档说「玛丽不直连存储，二者之间隔一层薄查询接口」，理由是"否则通用、可复用、可替换会退化成与这套存储绑定"。

**这个理由不成立**，因为：

> **"通用、可复用、可替换"说的是玛丽本身**——
> 同一个玛丽可以服务不同的目标；一个方法不好使，随知识更新换一个方法。
> **它不是指存储。**

所以：

| | 结论 |
|---|---|
| **存储** | **只有一套**。一个由玛丽组成的系统**必须**和这一套存储绑定。这是正常的，不是缺陷 |
| **玛丽** | 通用、可复用、可替换。这靠"玛丽以指标定义、不持有长期状态"实现，与存储无关 |
| **中间层** | 不需要为了"可替换"而存在 |

**保留的只有一件事：工程整洁**——把图上的读写集中在少数几个函数里，而不是让 Cypher 散落在各处。这是代码组织，不是架构契约。

---

## 二、玛丽的动作，与它对应的存储操作

玛丽干的事（`02` 的职责）：**把目标拆成子目标 → 分给其他玛丽 → 收观测 → 按误差从记忆里选方法 → 缩小误差，缩不了就上报。**

对照到存储，它只需要三件事：

```
① 读知识   这个指标怎么拆？有哪些方法？各方法的适用条件与预期是什么？
② 读经验   这些方法过去表现如何？在什么条件下表现如何？有多少样本？
③ 写经验   记一条「发生了什么」
```

**就这三件。** 上一版列了四个动作（取原文切片、取概念邻域、取知识条目、取账目），其中**前两个与玛丽毫无关系**：

| 上一版的"动作" | 谁真的需要它 |
|---|---|
| 取原文切片 | **审计**（报告里每个数字回查原文）——不是玛丽的动作 |
| 取概念邻域 | **检索/RAG** 与**提炼**——不是玛丽的动作 |
| 取知识条目 | ✅ 玛丽要（拆解要逻辑、选方法要定义） |
| 取账目 | ✅ 玛丽要（按误差选方法，凭据就是经验） |

而且上一版还有一个硬伤：**它规定"只读"**——可玛丽的职责里明明有**记账**。**接口漏了玛丽一半的动作。**

---

## 三、① 读知识

**输入**：一个指标
**返回**：

| 内容 | 关键字段 |
|---|---|
| 指标元数据 | 规范名、别名、可观测性、检查周期、方向 |
| 拆解逻辑 | **版本**、输出指标、各输入指标及权重、形态（编译态/解释态）、对账精度 |
| 方法列表 | 每个方法：**版本**、适用条件、多维预期轨迹（含成本维度）、执行体、占用 |
| **每个方法附置信度** | **由经验现算**：样本量、起点条件的分组覆盖、预期命中率、前提未成立率 |

**两条硬要求：**

1. **必须带版本**（`提醒负责人@v3`），不能只给"当前最新"。
   > 因为未比对完的预测要按**生成时冻结的版本**对账。

2. **答不了要说"答不了"。** 如果这个指标没有任何拆解逻辑，返回的是**知识缺口**，不是空列表。
   > "缺口"和"没有"是两件事，而只有前者**带地址**。静默返回空，会让调用方把缺口读成结论——**那是最贵的一类错**。

---

## 四、② 读经验

**输入**：一个方法（或一个指标）＋ **可选的起点条件**
**返回**：一组**实践**，每条完整可取：

```
实践 #4711
  起点      2026-03-05，里程碑按期率 = 0.70
  依据      提醒负责人@v3
  动作      执行体 = 人，派发给：张工
  过程      +0天 0.70 / +3天 0.88 / +7天 0.86 / +14天 0.82
  终点      比对完成
  形状      14 天，4 个观测点
```

**为什么必须"每条完整可取"，而不是只给聚合结果**：因为**长度与内容大相径庭**。只给均值等于把形状不同的链压成一个标量——详见 [03](03-两层如何结合.md) 那张 37 次实践的分布表。

**返回顺序必须稳定**（按单调序号升序）：否则"同一输入两次调用结果不同"，回放与审计都不可信。

---

## 五、③ 写经验

**输入**：一条事件
**返回**：分配到的**单调序号**

**唯一的写入口。** 校验与分配都在这里完成：

| 校验 | 不通过就 |
|---|---|
| 事件类型在固定枚举内 | 拒绝 |
| 时间格式定宽（`2026-03-05T09:00:00Z`） | 拒绝 |
| 业务时间与入账时间都存在 | 拒绝 |
| 因果父指针若不为空，必须指向已存在的经验节点 | 拒绝 |
| **不允许半条** | 回滚整个事务 |

**三条不许**：

| 不许 | 为什么 |
|---|---|
| **不许修改任何已写入的经验** | 只追加。记错了就**再写一条更正记录** |
| **不许删除** | 同上 |
| **不许把知识内容抄进记录** | 只记 `提醒负责人@v3`。抄了内容，知识一改历史就对不上，而且**再也拆不开** |

## 六、写入纪律：退化成两层（因为选了 Neo4j）

选 Neo4j 就没有 SQL 那种"触发器直接拒绝 UPDATE"。纪律因此不再由数据库兜底，改成：

### 第 1 层 · 单一写入入口（硬）

**全系统只有一个函数能写经验**，而且它**只做新增**。
> 检查方式：全代码库检索"对经验层的写操作"，必须只出现在那一个模块里。**这条用脚本查，不靠自觉。**

### 第 2 层 · 独立审计（可发现）

既然不能"阻止"，就必须"**能发现**"。三条检查：

| 检查 | 怎么做 | 能发现什么 |
|---|---|---|
| **内容指纹** | 每条经验记录带写入时的**内容哈希**；审计重算并比对 | **被就地改过** |
| **序号单调** | 扫全部 `seq`，必须严格递增无重复 | 序号被弄乱、被回填 |
| **计数自洽** | 知识节点的世界计数 = 它的世界边 `count` 之和 | 计数脱节 |

**内容指纹是"只追加"的可检查化**：触发器能"拒绝"，哈希只能"事后发现"——**但发现本身就足以让纪律有意义**，因为审计是独立跑的。

### 两条纪律（对应 `D23` 基岩原则）

> **用来报告"经验是否被篡改"的机制，不能依赖经验本身。**

1. 审计必须**能独立跑**（不读被审计的库也能成立的部分：退出码、外部守护、独立告警通道）；
2. 审计的**结果不落在被审计的库里**。

---

## 七、实现期的三个坑（都会"不报错、只错"）

| 坑 | 后果 | 对策 |
|---|---|---|
| **序号由多处分配** | 顺序被打乱，回放与审计全废 | 序号**只**在单一入口分配 |
| **uid 用随机值** | 撤销后重建，指向旧 uid 的回退凭证永远对不上 | uid **确定性派生**（见 [04](04-数据模型.md) §二） |
| **把知识内容抄进记录** | 知识一改，历史对不上，且拆不开 | 只记 `key@版本` |

---

## 八、本篇不做的事

| 不做 | 为什么 |
|---|---|
| **不冻结接口** | 不为了"可替换"而冻结——存储只有一套 |
| **不做第二个实现** | 同上 |
| **不判"存储可替换"** | 同上。上一版为此写了 38 项验收，**整条作废** |
| **不在玛丽与存储之间加抽象** | 唯一的收益是工程整洁，而那是代码组织的事 |
