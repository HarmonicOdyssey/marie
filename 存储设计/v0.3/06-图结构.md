# 06 · 图结构

> **实现层第一篇。** 用知识图谱（不是 SQL 类库），落地[两样东西](01-两样东西.md)。
> 读这篇之前请先读 01–04。

---

## 一、三类节点

```
① 词汇     量（路程、耗电、电量）、对象（7号车、3号桩）、动作（充电、继续跑）、时间、位置
② 知识     一条知识 = 一个函数（输入量 → 输出量）+ 参数
            **正文是一个函数文件**，知识节点指向它
③ 发生     一组同期的（量, 值）；可以带"依据 / 选了 / 预期结果"
```

**为什么把"词汇"单独列出来**：**它是知识与经验共用的那批量。**

- 知识声明它**输入哪些量、输出哪个量**
- 发生记录**那些量当时的值**

**接缝就在这里**（见 [03](03-咬合.md)），不在别处。

---

## 二、关系

| 关系 | 从 → 到 | 用途 |
|---|---|---|
| **输入** | 知识 → 量 | 这条知识要哪些量 |
| **输出** | 知识 → 量 | 它算的是哪个量 |
| **代入** | 发生 → 量（**值挂在边上**）| 这一次发生里，各个量是多少 |
| **依据** | 发生（决策）→ 知识 | 这次决策用了哪条知识（**用于审计，不用于对账**）|
| **选了** | 发生（决策）→ 动作 | 选了什么 |
| **预期** | 发生（决策）→ 量（**值挂在边上**）| 决策当时算出来的预期结果 |
| **属于** | 发生 → 发生（实践）| 把若干条记录拢成"一次实践" |
| **取代** | 知识 → 知识 | 版本链 |
| **来源** | 发生 → 原文切片 | 溯源（若知识是从文本提炼来的）|

**"代入"这条边上带数值**，因为：**值相同 ≠ 同一个东西 → 值做属性，不做节点。**
（若把"22"做成节点，它会指向无数不相干的事实——**伪共享**。）

## 三、一张具体的图

```
【词汇】
  (量:路程) (量:载重) (量:天气) (量:耗电)
  (对象:7号车) (动作:继续跑) (动作:充电)

【知识】
  (知识:耗电估算@v3) {算法: …, 参数: …}
      ──输入──→ (量:路程) (量:载重) (量:天气) (量:车况)
      ──输出──→ (量:耗电)

  (知识:充电时机@v2) {算法: …, 参数: …}
      ──输入──→ (量:电量) (量:排队时长) (量:任务紧不紧)
      ──输出──→ (量:当班圈数)          ← 它预期的结果

【经验 · 一次发生】
  (发生#4711) {发生:14:20, 记账:14:20}
      ──代入{值:4.2}──→ (量:路程)      ← 绕路了，本来 3.5
      ──代入{值:90} ──→ (量:载重)
      ──代入{值:雨} ──→ (量:天气)
      ──代入{值:7}  ──→ (量:耗电)

【经验 · 一次决策】
  (发生#4712) {发生:11:05, 记账:11:05}
      ──依据──→ (知识:充电时机@v2)
      ──选了──→ (动作:继续跑)
      ──预期{值:11.5}──→ (量:当班圈数)

【对账】
  取出知识声明的输入量与输出量的值 → 算 → 比 → 残差
  缺任何一个 → 报「缺输入」，并指出缺哪个
```

**图上只有"谁连着谁"和"那些量当时的值"。**
**对账是一段通用的取数-计算-比对逻辑，不需要为每类知识写一套。**

## 四、四个实现要点

### 4.1 两条时间，都记

| 字段 | 回答什么 |
|---|---|
| **何时发生** | 这件事在世界的哪个时刻 |
| **何时记进系统** | **系统在那一刻知道什么** → 防止用"后来才知道的"解释"当时的决定" |

**平时两者相同。补录、延迟上报时不同——那时第二个才显出用处。**

### 4.2 派生量不存

```
排队 40 分钟 = 开始充电(08:55) − 派往桩3(08:15)     ← 算出来的
残差、命中率、解释率                                  ← 全是算出来的
```

**只存原始时刻与原始值。** 存派生量迟早会和原始记录打架，而打架时你不知道该信哪个。

### 4.3 知识节点指向一个**函数文件**

```
(知识:耗电估算@v1) {文件: functions/power/v1.py}
(知识:耗电估算@v2) {文件: functions/power/v2.py}
(知识:耗电估算@v2) ──取代──→ (知识:耗电估算@v1)
```

**版本就是另一份文件 + 另一个节点。** 就这么简单——**它是数据存储，不是版本控制**。

> **凡是"diff、分支、审查流程"这类东西，都不在玛丽的范围内。**
> 那是**业务落地时按具体场景再定的**事。
> 玛丽只需要知道：**这一版指向哪个文件**，以及**它取代了哪一版**。

### 4.4 发生记录需要单调序号

**顺序的唯一依据是序号，不是时间戳**——同一时刻可以有多条记录，而且时间戳可能被回填。

图谱库通常**没有自增主键**，所以序号要自己维护（一个计数器，在同一次写入里自增）。
**只能由单一写入入口分配**（见 [07](07-写入纪律与归一化.md)）。

## 五、世界 = 可见性标记

**别把它当成"另一个现实"。**

```
最笨的实现：每个应用一套独立的数据库
多世界的实现：**同一套数据库**，数据上标记"可见给谁"
```

| | |
|---|---|
| **是什么** | 数据上的一处**可见性标记** |
| **干什么** | 权限、不同用户、游戏内多个 AI、多场景复用 |
| **不是** | 不是"另一个现实"，不是对象，不是维度 |

**注意：知识是共用的**（同一套库），只是**可见性**不同。所以"'一个世界的经验能不能检验另一个世界的知识'这个问题不存在"。

**唯一要求**：**必须能"只看到一个可见范围"地查询**，而不是查完再过滤。
因为**放到查询端过滤，它一定会在某个连接处漏掉**——而那种漏是**静默的**。

## 六、不放进图的东西

| 不存 | 怎么来 |
|---|---|
| 排队时长、单趟耗时、脱产时间 | 由原始时刻算 |
| 残差、命中率、解释率 | 由发生记录 + 知识算 |
| 这条知识有多少证据撑着 | 取数比对之后计数 |
| 当前是哪一版知识 | 看"取代"边的方向（没有人指向它的那个就是当前） |
| 每条记录属于哪一类 | **不需要**——知识的输入量本身就是筛选条件 |

## 七、一处曾经的错误设计（留作教训）

**曾经设计过一个「主体」维度**，理由是"40 辆车 → 有对照 → 能造反事实 → 能谈因果"。

**而"归因不重要"那条否掉了整个需求**，这个维度就成了多余的：

- "观测挂在某辆车上" → 用 `代入` + `(对象:7号车)` 就够
- "条件里含哪辆车" → 输入量里引用那个对象就行
- "多个单元可比" → **不需要**

**7号车就是一个普通词汇节点。**
