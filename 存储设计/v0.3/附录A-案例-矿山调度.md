# 附录A · 案例：封闭场景无人车调度

> **案例的作用是论证"这套设计哲学和思路是对的"，不是做方案细化。**
> 所以下面**只写能检验设计的部分**：每条设计在这里有没有具体内容、能不能跑起来。
> 工程约束、业务指标是否全面，一律不展开。

---

## 一、场景（三句话）

```
封闭场景、固定路线、固定载重的一支无人车队。
要保证：剩余电量安全、有序充电、按期点保维；
在此前提下：尽可能多跑几圈。
```

**效率指标 = 当班圈数。** 数据里**有动作序列**（充电、维保、调度决策），**没有"为什么"**。
数据是一段历史，持续流入。

---

## 二、用这个场景检验[玛丽的循环](02-玛丽的循环.md)

```
① 目标 A = 当班圈数
② 拆解   圈数 = (当班时长 − 脱产时间) ÷ 单圈周期          ← 知识（输入量 → 输出量）
③ 观测   脱产时间、单圈周期 都能从遥测与动作记录会计出来   ← **可观测 ✅**
④ 对账   实际圈数 vs 目标
⑤ 决策   超差 → 选一个方法（错峰充电 / 合并作业 / 就近选桩）← 知识
⑥ 记录   记下：当时的条件、依据了哪几条知识、选了什么、结果如何
⑦ 反省   经验回来检验知识
```

**循环跑得通。** 而且这里能看出"**记全输入**"为什么是分水岭：

```
耗电估算：每跑一圈就产生一个样本（输入：路程/载重/天气；输出：耗电）
充电时机：每次决策 + 执行才产生一个样本

→ **只要输入输出都被观测到，样本就是免费的**
→ 而**任何一个量没被观测到，这一次就不构成证据**（报「缺输入」）
```

---

## 三、用这个场景检验[输入量的四条要求](04-知识该长什么样.md)

```
知识：当班圈数 = (480 − 脱产) ÷ 单圈周期        ← 一种表达：输入量 → 输出量
```

| # | 要求 | 在这个场景里 |
|---|---|---|
| **1** | 输入量**可观测** | ✅ 三个量都能从遥测 + 动作记录算出来 |
| **2** | 输入量**不冗余** | ✅ 脱产 与 单圈周期 各取不同值 |
| **3** | **残差没有结构** | ❌ **有结构**！残差与"任务时段电量"相关 −0.52 → **发现漏了"低电量限速"** |
| **4** | （分工类）输入量**有手段** | ⚠️ 脱产有手段（错峰/合并/就近/加桩）；**单圈周期没有** |

**判据 4 在这里给出了一个真实结论**：

> **单圈周期没有手段 → 它不该被派给一个玛丽，只能做这条知识的一个输入量。**

**这就是"量 ≠ 玛丽"**：量是坐标，玛丽是"有人能对它动手"。
**如果没人能影响它，给它一个玛丽，等于让它每班报一次"我改变不了它"。**

## 四、用这个场景检验[独立性判据](04-知识该长什么样.md)

**独立 = 自由度不冗余。** 这个场景里有一个**看起来很诱人、其实是错的拆法**：

```
❌ 拆成 "充电脱产" + "维保脱产"

   它们抢同一个资源（车辆的在位时间）：
   一个变了，另一个也被决定
   → 一个自由度写成两个 → 冗余
```

**正确做法**：**把它们合成一个子指标。**

```
✅ 拆成 "场站作业总脱产"（一个子指标）
   它有自己的手段（错峰、合并、就近、加桩）
   它有自己的观测（会计可算）
   → 一个自由度，一个玛丽
```

**这验证了一条推论**：**凡是需要"在两个玛丽之间分配额度"的地方，就是没拆开的地方。**
**分配应当在内部由知识完成，不需要在两个玛丽之间发生。**

> **注**：这个场景里充电桩和维保工位是**两套设施、两个队列**。
> 若它们真共用一条队列，判据同样会报出来——**共用会让"一个变了另一个也被决定"。**

## 五、用这个场景检验["报警不判决"](05-建模玛丽.md)

**这里给出的例子最干净：**

```
报警：子指标「单圈周期」没有任何方法能影响它
     位置：拆解「圈数 = (480 − 脱产) ÷ 单圈周期」@v1

两种相反的含义：
  (a) 它不该在拆解里 —— 交付不出去，不是"下游能干活的子指标"
  (b) 该有方法，只是还没被发现或登记（比如换更省电的车）

系统分不清是哪种
  → 只能说「它目前没有手段」，不能说「去掉它」
```

**而如果把"可观测"错当成"该有玛丽"，后果是实打实的**：
那个玛丽会**每班报一次"我改变不了它"**，把报告层塞满，**而它什么都没干。**

## 六、用这个场景检验[解释率](05-建模玛丽.md)

```
解释率 = 能被解释的决策数 ÷ 总决策数

"这个决策被解释了" = 有一条知识，它：
   ① 适用条件覆盖这次决策的情境
   ② 预期与实际观测相符
```

**在这个场景里它跑得动**，因为：

| 需要的 | 场景里有 |
|---|---|
| 决策可寻址 | ✅ 每次充电/维保/调度都带时刻与依据 |
| 条件可判定 | ✅ 电量、排队、任务量都是数据里有的量 |
| 预期可核对 | ✅ 脱产、圈数都可会计 |

**而"解释不了的那部分"就是知识地图上的空白** —— 它同时驱动"补知识"和"修知识"。

---

## 七、这个场景揭示的两处设计内容

**这两条不是从哲学推出来的，是从看真实场景看出来的——所以它们值得单列。**

### 7.1 红线要用**下尾**看，而且红线之间会耦合

```
最低电量：均值 31.4%（看着很安全）／最小 11.4%（破线）
```

**均值完全掩盖了破线。** 而且那次破线发生在"排队 47 分钟"时：

```
排队 → 等待 → 耗电 → 破线        这是物理链条，不需要统计
```

**所以该设约束的不只是"最低电量"，还有"充电排队时长"。**

### 7.2 防患型动作要用"不良事件率"衡量，不能用"涨幅"

充电**不提升圈数**——它**避免更坏的情况**（半路没电）。
用"圈数涨了多少"去衡量充电，会得出"**充电有害**"（充一次就少跑半个班）。

**这两条都落回同一条设计**：**知识的"破了怎么办"属性**（见 [04 §五](04-知识该长什么样.md)）——红线是"破了要上报"的那类条件。

---

## 八、这个场景**没**揭示的东西

**如实标出来，免得误以为设计已经完备：**

| 没揭示 | 为什么 |
|---|---|
| **多世界（权限/用户）** | 这个场景只有一个现实 |
| **从文本提炼知识** | 这个场景没有 SOP，知识从数据长出来 |
| **多玛丽协作的复杂性** | 这个场景的拆解链很短（三级） |
| **长周期知识** | 历史只有一段，还没遇到"几年前的知识还准不准" |
