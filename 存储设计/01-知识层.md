# 01 · 知识层

> 知识层存**普遍的**东西：世界**通常**是什么样的。
> 它不存"某一次发生了什么"——那在[经验层](02-经验层.md)。

---

## 一、知识层里有什么

四类内容，**共处一张图**：

| 类别 | 是什么 | 例子 |
|---|---|---|
| **概念与关系** | 由文本提炼出的概念，以及概念之间的关系 | 指标、方法、角色、系统、事实 |
| **拆解逻辑** | 指标 Y 怎么摊到它的输入指标上 | "里程碑按期率 ← 任务完成率 + 阻塞数" |
| **方法定义** | 能影响某个指标的可执行动作 | "提醒负责人：条件、预期、执行体" |
| **玛丽定义** | 一个玛丽负责哪个指标、依赖什么、有哪些方法 | "M-按期率：输出里程碑按期率，输入任务完成率" |

**它们不是四张表，是同一张图上的节点与关系。** 这是本设计的基线：**知识与经验用同一套结构**（详见 [02](02-经验层.md) 与 [04](04-数据模型.md)）。

---

## 二、节点与关系（两套一层共用）

### 节点类型：六种，不增不减

| 代号 | 名称 | 定义 | 允许带 |
|---|---|---|---|
| `g` | 普遍概念 | 一类事物或属性的概括（"服务器"、"促销活动"） | 名称 |
| `s` | 单独概念 | 特定的单个实体（"张三"、"DB-01"、"提醒负责人@v3"）。**时间和地点除外** | 名称 **或** 描述（二选一） |
| `t` | 时间 | 明确的时间点或时间范围（"2026年3月"、"今年元旦"） | 名称 |
| `l` | 位置 | 明确的地点或空间范围（"北京"、"3号仓库"） | 名称 |
| `f` | 事实 | 行为动作、状态变化、属性特征、实体间关系、示例 | 描述、语气、极性 |
| `r` | 非文本资源 | 代码块、图片、表格等 | 资源类型 + 存储位置 |

### 关系类型：八种（七种概念关系 + 一种溯源关系）

| ID | 名称 | 源 → 目标 | 语义 |
|---|---|---|---|
| 1 | 实例 | `s` → `g` | 单独概念是普遍概念的一个实例 |
| 2 | 是 | 概念 → 概念 | 两者指同一个东西 / 同义 |
| 3 | 属于 | 概念 → 概念 | A 是 B 的一部分或一员 |
| 11 | 参与 | 概念 → `f` | A 参与了事实 B |
| 12 | 发生 | `f` → `t`/`l` | 事实 A 发生在时间或地点 B |
| 13 | 导致 | `f` → `f` | 事实 A 导致了事实 B（**纯因果**） |
| 14 | 先于 | `f` → `f` | 事实 A 先于事实 B（**纯时序，不含因果**） |
| **21** | **来源** | `f` → **`:Slice`** | **溯源：这个事实出自哪段原文** |

**两条纪律：**

1. **`13` 与 `14` 分开**，不许合并。理由：marie 的纪律是"**不做因果推断**"——如果 `13` 把"因果"和"时间先后"混在一句里，那么图谱里每一条"先于"都会被读成因果断言，**等于系统在用知识层偷偷做因果推断**。分开之后，`13` 只能是"知识里被声明的因果"，`14` 是可从时间线观察到的事实。
2. **方向由我们自己定，由约束强制**。不依赖任何外部文档的准确性。
   - 新增关系从 **44** 起编号（1–3、11–14 已用；21–43 留空）。

### 每条关系都可以带"实际执行与声明"（用于经验层，见 02），但知识层只用与声明相关的那部分。

## 三、指标：玛丽的锚点，也是词汇表

**指标是知识层里最要紧的东西**——玛丽就是"负责一个输出指标的组件"。

| 指标元数据 | 例子 | 为什么要有 |
|---|---|---|
| 规范名 | 里程碑按期率 | 复用的前提。**同义异名会让复用静默出错** |
| 别名 | ["按期率", "里程碑达成率"] | 承接不同人的叫法 |
| 可观测性 | `可直接观测` / `可再分解` / `都不能` | **数据缺口的判据** |
| 检查周期 | 1 天 | 不同指标可以不一样（客流按小时，利润按天） |
| 方向 | 越高越好 / 越低越好 / 守住区间 | 对账时判"好"还是"坏" |

> **指标词汇的规范化是必须先做的前置工作**：同义异名（"客流 / 客流量 / 到店人数"）会让复用失败，同形不同义（"完成度"在不同场景指不同的量）会让复用错。这件事不做，池子再厚也接不上。

## 四、知识条目之一：拆解逻辑

**一句话**：指标 Y **怎么摊到**它的输入指标上。

```yaml
条目: 拆解-里程碑按期率
版本: v2
输出指标: 里程碑按期率
输入:
  - 指标: 任务完成率
    权重: 0.6
  - 指标: 阻塞数
    权重: 0.4      # 负数方向：阻塞越多，按期率越低
形态: 解释态          # 见下"编译态 / 解释态"
对账精度: 粗          # 见下
```

**两态之分**（不是两种存储，是一个属性）：

| | 编译态 | 解释态 |
|---|---|---|
| 形态 | 能写成确定性规则的（公式、阈值、分档） | 保留自然语言描述 |
| 执行 | 编译一次，之后确定性执行 | 每次执行时当场读、当场判断 |
| 优点 | 快、便宜、行为一致 | 能承载抵抗代码化的内容 |
| 风险 | 只覆盖可以形式化的部分 | 判断可能漂移 |

**解释态必须降低对账精度**：如果预期是一句自然语言，硬判"是否超差"就是**制造虚假精度**——而虚假精度比粗糙更危险，因为它看起来可审计。所以解释态**只报环比突变与趋势反转**，不报超差。

**同一份拆解可以一半编译态、一半解释态**，不必强行统一。

## 五、知识条目之二：方法定义

**一句话**：能影响某个指标的**可执行动作**，带适用条件、多维效果预期、执行体。

```yaml
条目: 提醒负责人
版本: v3
影响的指标: 里程碑按期率

适用条件:                     # 对当前状态的断言，选择前先过滤
  - 里程碑按期率 < 0.95

效果预期:                     # 多维，地位平等，含成本维度
  - 维度: 里程碑按期率
    轨迹:
      - { 距起点: 3天,  预期: +0.20, 容差: ±0.05 }
      - { 距起点: 14天, 预期: +0.15, 容差: ±0.08 }
  - 维度: 团队打扰成本
    轨迹:
      - { 距起点: 3天,  预期: +1次/人, 容差: ±1 }

执行体: 人                     # 人 / 机器 / 外部接口
占用: [{ 类型: 人力, 数量: 2, 单位: 人时 }]
```

**四处最容易被写错的地方：**

**① 效果预期是"轨迹"，不是"一个数"。** 上例是"3 天涨 0.20、14 天涨 0.15"——**随距起点的距离展开**。远期自带更宽的容差带（±0.08 比 ±0.05 宽），**这是诚实，不是缺陷**：预期越远越不确定。
> 这一条直接决定了[两层怎么对照](03-两层如何结合.md)：因为预期是按"距起点"写的，所以不同长度、不同起止日期的实践**才能互相比较**。

**② `执行体` 是整个定义里最要紧的一个字段。** 它决定"执行"这个动作实际长什么样：

| 执行体 | 执行实际是什么 |
|---|---|
| **人** | 向某人提一条建议。系统记"已派发"，等观测回流 |
| **机器** | 系统自己操作 |
| **外部接口** | 调用一个外部系统 |

架构对三者**一视同仁**：都是"选择一个方法并执行"。所以**不需要"提议通道"和"执行通道"两条路**，也不存在"方案待批"这种特殊状态——需要人签字的场景里，"申请批准"本身就是一个 `执行体: 人` 的方法。

**③ 多维效果地位平等，不区分"主效果"和"副作用"。** "预算不超支"本身就是一个目标，超支就是那个目标上的误差，走完全相同的对账通道。
> 副作用只是**记账时没预料到的效果维度**；给它一个特殊身份，等于承认"我们没预料到的那些不重要"——而那恰恰是复盘最需要的。

**④ 适用条件必须是"对当前状态的断言"。** 它决定"选这个方法之前先过滤掉什么"。

## 六、知识条目之三：玛丽定义

```yaml
玛丽: M-里程碑按期率
版本: v1
输出指标: 里程碑按期率
输入指标: [任务完成率, 阻塞数]
拆解逻辑: 拆解-里程碑按期率@v2      # 引用，不是内容
可用方法: [提醒负责人@v3, 调整排期@v1]
缺口策略: { 拆不动: 报知识缺口, 无方法: 报方法缺口 }
```

**两条约定**：

- 定义里**不出现场景词汇**。输出指标是"里程碑按期率"这个**指标引用**，不是某家公司的某个项目。
- 定义**不带实现细节**。它是编译成代码执行、还是每次由语言模型解释，是运行期的事，不是定义的事。

## 七、知识层的写入纪律：可修订

| 机制 | 怎么做 |
|---|---|
| **同一件事再出现** | **不新建节点**，把该节点的**出现计数加一**。于是"高频概念"天然成为热点，不需要跑昂贵的图聚类 |
| **发现记错了** | 改。知识层是**诠释**，可以被质疑、回查、推翻、重编 |
| **修改一条知识条目** | **追加新版本**（`提醒负责人@v4`），旧版本永久保留。引用永远是 `key@版本`，不是"当前最新" |
| **源文变了** | 派生自它的条目**自动失效**，需要重新编制（详见下） |

### 为什么"知识只追加版本"，而图谱节点可以就地改

因为**两类东西不同**：

- **条目**（拆解逻辑、方法定义）是**可执行的依据**，要能回答"3 月 5 日当时依据的是哪一版" → 必须不可变，只能追加版本
- **图谱**（概念与关系）是**概括**，本来就该随证据增长而修订 → 就地合并计数是对的

**它们的差别不在结构（结构相同），在纪律。**

## 八、什么**不**进知识层

这一节是上一版设计的重大修正。

| 东西 | 例 | 进不进知识层 | 为什么 |
|---|---|---|---|
| **指标的值** | 里程碑按期率 = 0.88 | **不进** | 知识是普遍的。0.88 是"某一次"的事实，属于经验层 |
| **具体时间点** | 2026-03-05 | **不进**（作为"指标的值"的一部分） | 同上。"每月第一个工作日"这种**规则**可以进 |
| **型号 / 编号 / ID** | `DB-01`、`V1.5`、`#4711` | **不进** | 它们是个体标识，属于经验层 |
| **事实文本描述里的数字** | "障碍物距离小于 2 米" | **可以** | 那是自然语言，不是可计算的数值列 |

**一条判据**：**知识层里不存在可以拿来做算术或排序的数值。** 如果某个数字需要参与对账（比大小、算误差），它属于经验层。

> 反面例子（**不要这样**）：把 `里程碑按期率` 节点的属性设成 `值: 0.88`。那样就能写 `WHERE 值 > 0.5` 地筛节点——**把对账混进了知识检索**，而知识层根本没有"当前值"这个概念。

## 九、一个完整的知识层片段（沿用全套的例子）

```
(g) 里程碑按期率                    ── 指标
(g) 任务完成率                      ── 指标
(g) 阻塞数                          ── 指标
(g) 提醒负责人                      ── 方法（类）
(s) 提醒负责人@v3                   ── 方法的具体版本
(s) M-里程碑按期率@v1               ── 玛丽定义的具体版本

(s) 提醒负责人@v3  --1 实例-->  (g) 提醒负责人
(s) 提醒负责人@v3  --11 参与--> (f) 「提醒负责人 影响 里程碑按期率」
(f) 「提醒负责人 影响 里程碑按期率」 --11 参与-- (g) 里程碑按期率
(s) M-里程碑按期率@v1 --11 参与--> (f) 「M-里程碑按期率 输出 里程碑按期率」

归属关系：
(s) M-里程碑按期率@v1 --3 属于--> 拆解-里程碑按期率@v2
(s) M-里程碑按期率@v1 --3 属于--> 提醒负责人@v3
```

**注意这里没有任何数值。** `+0.20`、`±0.05` 这些是**方法定义条目里的属性**，不是图上的节点，也不参与图查询——它们只在[对照与聚合](03-两层如何结合.md)时被读出来算。
