# 08 · 实施计划

> 目标：用最小的工作量做出一份**不破环架构、不预留返工**的 POC。
> 估算前提：开发在 AI 辅助下进行。AI 能省的是标准工程量，省不动的是调试与逻辑正确性——估算里已经分别标出。
> 场景：项目管理（拆解开发任务、排期、每日收发日报、跟踪进度、报风险）。

---

## 一、范围与原则

### 1.1 这次要证明什么

| 主张 | 靠什么证明 |
| --- | --- |
| 账目立得住 | 重放一致性、审计链、误差不落库（J6） |
| 持续运营与逼近 | 20 个节拍的误差曲线、正常运转不推送（J5） |
| 一池多用 | 同一批原子实体装出两个场景（树 + 森林）（J1） |
| 内核零改动 | 第二个场景接入时内核 diff = 0（J3） |
| 装配成本下降 | 复用率与装配人时逐次下降（J2） |

### 1.2 两条纪律

1. **账本先行。** M1 不接任何场景。如果某件事无法在账本上表达，环路怎么设计都没用；
2. **每期结束都有一条"不通过就停"的闸门。** 不通过不进入下一期，也不靠延长工期掩盖。

### 1.3 六个零成本纪律（第一天起守，做错了必然返工）

| 纪律 | 做错的代价 |
| --- | --- |
| 事件负载用自由 JSON；核心字段只放通用词汇 | 要迁历史账 |
| 引用知识一律 `key + version`；**不许把知识内容抄进事件** | 知识改了历史无法重算 |
| 误差绝不落库，只存观测与生成预测时冻结的预期 | 账目失去可重算性 |
| 单一写入入口 | "序号即顺序"的前提崩掉，重放失效 |
| 重放只读；副作用先入账再执行 | 重放不幂等，审计不可信 |
| 内核里零场景词汇 | 分离性失效，第二个场景推倒重来 |

这六条几乎不花时间，**但是这份计划里唯一不能被工期压力挤掉的东西**。

## 二、工作方式：按碎片时间排

开发是抽空闲与下班后做的，不是连续投入。所以下面的工期是**有效工作时间**，落到日历上要打折。

### 2.1 有效时间换算

| 假设 | 换算 |
| --- | --- |
| 每晚 2–3 小时，每周 4–5 晚 | 每周约 10–13 小时 = **1.5–2 个工作日** |
| 11–15 个有效工作日 | 约 **6–9 个日历周** |
| 若白天能零星推进（会议间隙、跑测试等） | 可压到 **5–7 个日历周** |

### 2.2 两类工作，排法完全不同

| 类型 | 内容 | 排在哪 |
| --- | --- | --- |
| **适合碎片**（估计占 60%） | 写 schema 与测试、配置加载、报告模板、第二个场景配置、文档 | 每晚 1–3 小时一段。**AI 能大段生成，你主要负责校对** |
| **需要连续**（估计占 40%） | 重放一致性、断裂降级、误差取数逻辑校准、验收判据核对、架构决策 | 必须留整块时间。这类问题**丢了上下文就要重新想一遍**，碎片时间做等于反复重启 |

**关键动作：把第一类尽量堆到碎片时间，把第二类集中到你能拿到整块的时段。** 判断标准很简单——如果一个任务中断后需要重新回忆超过十分钟，它就属于第二类。

### 2.3 每次开工的固定动作（三分钟）

```
1. 跑一遍测试套件，确认现在是绿的（红的话先修，或者退回上一个 good 提交）
2. 读任务清单，确认今天这一段做哪个
3. 跑结束时把任务勾掉、写一条 DECISIONS.md、提交
```

这条纪律的价值在于：**下次开工时，你要复原的状态在仓库里，不在记忆里。** 这正是这套架构自己的原则（状态在存储、不在脑子里）用在开发流程上。

### 2.4 两个必须建立的文件

| 文件 | 作用 |
| --- | --- |
| `DECISIONS.md` | 每做一个取舍追加一条：日期、决定了什么、为什么。碎片时间最大的风险是**深夜做的决定，第二天忘了理由**，然后重新推翻一遍 |
| `NEXT.md` | 只写"下次开工先做什么"，一两行。不写进度报告 |

### 2.5 用 AI 扛住"接不上上下文"的那部分

- **测试放在前面写。** 测试是碎片时间唯一的自动化守门员：有了它，你可以让 AI 去修 bug，第二天跑一遍就能确认，不必读代码；
- **调试也交给 AI 主导。** 你只提供症状与判据（"重放两次结果不一致，判据在 J6 第三条"），它写失败测试、定位、修、给你一份改动说明让你复核。硬调试强依赖连续上下文——正好是 AI 最该接手的部分；
- **不要让 AI 替你改架构。** 决策必须你清醒的时候做，并留进 `DECISIONS.md`。

### 2.6 三个现实风险

| 风险 | 对策 |
| --- | --- |
| **半成品分支**：晚上做到一半要睡，第二天不知道改到哪 | 每个任务切到"1–2 小时能收尾"的大小；每次收尾都要让仓库处于可运行状态，哪怕功能没完成 |
| **改了半天没进展**：碎片时间里最容易发生的挫败 | 维持一个"已知良好提交"标签，允许随时退回重来，不背着半成品往下走 |
| **拿这个系统管这个项目**（自指） | 坚决不干。本期它只是被开发的对象；开发进度用 `NEXT.md` 与提交历史管就够 |

### 2.7 对工期估算的影响

- **M1 的调试部分（1.5–2 天）要按最坏情况排**：它属于第二类工作，碎片时间下可能拉长到 3–4 个日历周；
- **M2、M3 反而好排**：配置、模板、第二个场景大量是第一类工作，可以切成小段；
- 结论：**别按周设里程碑，按"测试变绿"设里程碑。** 绿灯是唯一与时间投入无关的进度信号。

## 三、M1 · 账本与知识层

**工期 3–4 天**（其中约 1.5–2 天是调试，AI 压缩不了）

### 3.1 工程产物

| 模块 | 内容 |
| --- | --- |
| 事件表 | `id`（序号即顺序）、`tick`、`recorded_at`、`world`、`type`、`caused_by`、`snapshot_id`、`knowledge_ref`、`payload`（JSON） |
| 快照表 | 结构与事件表解耦，仅作回放锚点 |
| 写入入口 | 单一 `append(event)` 函数，串行化。**不允许第二个写入路径** |
| 重放器 | 最近快照 + 按序重放其后事件；重放全程只读 |
| 投影一：误差 | `观测 × 生成预测时冻结的预期`，现算，不落库 |
| 投影二：审计链 | 沿 `caused_by` 上溯至最初的目标 |
| 投影三：方法账目 | 按方法聚合执行事件与观测序列（次数、平均效果、样本量） |
| RQI | 四个方法：`slice` / `concepts` / `entries` / `ledger`；先实现一个后端（YAML + Git 的桩） |
| 知识版本 | 知识条目带 `key + version`；版本用 Git 提交标识承载 |

### 3.2 验收闸门（J6 五条全过）

- [ ] **状态重建**：任取一个时刻，`最近快照 + 重放其后事件` 与当时实时值逐字段相等；
- [ ] **审计链**：任取一次方法选择，沿因果父指针上溯到最初的目标，链路完整；
- [ ] **重放一致性**：同一段事件流重放两次，"当时的候选集与排序"逐字节一致；
- [ ] **断裂降级**：抽掉一条中间事件后，系统报错退出或输出降级报告，**不许静默产出错账**；
- [ ] 运行时数据库里**不存在**任何误差列或误差表（`sqlite_master` 检查输出为空）。

**闸门不通过就停。** 尤其第三条与第四条——它们证明的是"账目可信"，后面所有能力都建在这上面。

## 四、M2 · 环路与场景绑定

**工期 4–5 天**（AI 加速明显，配置与模板类工作量集中在这里）

### 4.1 工程产物

| 模块 | 内容 |
| --- | --- |
| 配置加载 | 场景配置声明式描述组件、连接、指标、容差带 |
| 组装 | 按配置装出单目标树；产出组件图与缺口清单 |
| 拆解规则 | 需求 → 任务的规则（每个任务 ≤ 1 人日、带唯一验收物） |
| 排期规则 | 有依赖按拓扑排序；无依赖按优先级与人力容量排 |
| 方法库 | 四个方法，执行体全为 `human`：提醒负责人 / 上报主管 / 调整排期 / 削减范围 |
| 运行循环 | 观测 → 现算误差 → 判定（超容差？有方法？）→ 执行 → 生成预测 → 记执行事件 |
| 心跳 | 预测到期未观测、数据源静默 |
| 观测接入 | 命令录入 + CSV 导入（工时、风险标记、提交/PR 合并） |
| 报告 | Markdown 死模板；**不用 LLM**，顺便留下基线 |

### 4.2 日循环（这个场景的核心动作）

```
早上    从账本与知识重新组装 → 现算昨日比对
        → 输出每人一份待办：今天做什么、优先级、有无卡点
        → 输出一份风险清单：谁超期、哪块投入不足
白天    人干活，系统不介入
晚上    收观测：工时投入（声明）、风险标记（声明）、提交与 PR 合并（实测）
```

### 4.3 验收闸门

- [ ] 单目标树连续跑 20 个节拍（批量压缩执行即可，不必等真实 20 天）；
- [ ] 产出误差随时间的曲线，误差被压入容差带并保持稳定；
- [ ] **正常运转生效**：进入容差带后主动推送显著减少，账目与报告层照常累积；
- [ ] **报告分层生效**：全部执行结果都进报告层；上报只包含缺口、预测失准、异常三类；
- [ ] J6 五条在真实数据下复测。

## 五、M3 · 第二个场景与复用率

**工期 4–6 天。这是唯一不能省的一期。**

单跑一个场景只能证明"环路能通"——那件事几乎必然成立，证明不了架构。通用性主张只有第二个场景能验。

### 5.1 工程产物

| 模块 | 内容 |
| --- | --- |
| 第二个目标 | **同一场景的第二个并行目标**（例如第二个项目），与第一个共用同一批原子实体，装出森林 |
| 复用率统计 | 所需指标数 / 新增组件数 / 复用组件数 / 装配人时 |
| 内核纯度检查 | 禁用词词表 + 每次合并前的内核目录 hash 比对 |
| （可选）跨领域场景 | 若工期有余，换一个结构完全不同的场景（机器执行、高频），信号更强 |

> 为什么第二个目标是"同一场景的项目二"而不是"换一个业务领域"：森林判定只要求**共享同一批原子实体**，项目二能立刻满足，成本最低。跨领域换场景列入推迟项（见 §六）。

### 5.2 验收闸门（硬验收）

- [ ] **J1**：同一批原子实体装出树与森林；两者**不引入任何新的内核概念、不给事件表加列**；
- [ ] **J3**：第二个目标接入时，内核目录 diff = 0 行；禁用词检查零命中；事件表 schema 未增加任何列；两个目标共用同一份内核与主干分支；
- [ ] **J2**：记录复用率与装配人时，第二次明显低于第一次；产出缺口清单，缺口带位置。

## 八、风险与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | **进度是主观填报**，全部观测都是"声明"，对账退化成观点比对观点 | 用情态区分：工时与完成标记记 `declared`，提交与 PR 合并记 `observed`；声称与实测**绝不混用**，不一致时不判断谁假，只报"对不上"（横向对账） |
| R2 | 日报填报摩擦大，两周后数据烂掉 | 把"日填报 ≤ 2 分钟"写成硬指标；早上的待办清单本身就是填报的回报 |
| R3 | 重放一致性与断裂降级调不通 | 这两条放在 M1 闸门里，**不通过就不进 M2**，不许带着隐患往下做 |
| R4 | 误差取数逻辑写错（跟哪条预测比、版本怎么选） | 逻辑错误不报错、只算错。用"改一次知识预期、重算历史差异变化"来反证 |
| R5 | 拆解规则写得太粗，系统频繁报缺口 | 这本身就是有效结论。规则写得清不清楚，是 POC 要回答的问题之一 |
| R6 | 时间与节拍的对应混乱（真实一天 vs 模拟节拍） | 统一用 `tick` 作为业务时间，`recorded_at` 作为入账时间；批量回放时两者不同步是正常的 |
| R7 | 为了赶工把六个零成本纪律破坏掉 | 纪律清单列在 §1.3，逐条在 M1 闸门里检查 |
| R8 | **碎片时间导致的上下文丢失**（深夜的决定第二天忘了理由、半成品分支接不上） | 建立 `DECISIONS.md` 与 `NEXT.md`；每个任务切到 1–2 小时能收尾；维持"已知良好提交"可随时退回（见 §二） |

## 十、开工前的第一件事（半小时）

在写任何代码之前，先确认三件外部条件，它们决定后面的设计：

1. **提交与 PR 记录能不能自动拿到？** 如果能，账本就有实测锚点；如果只能靠人手工填，那整个对账会退化成观点比对观点（见 R1）；
2. **谁每天填日报、填什么、花多久？** 这份填报表就是最早的观测接口定义；
3. **第一个项目的需求与任务能不能列出来？** 它同时是配置文件的原料和拆解规则的试金石。
