# 07 · POC 验证计划

> 本篇回答：怎么用一次最短的实验，验证这套架构的通用性主张。
> 待决事项见 §七；应用场景示例见附录 A。

---

## 一、验证什么

**验证目标是这套架构能不能用同一批原子实体装出不同场景的系统，不是某个场景的系统好不好用。**

架构的通用性主张有四条，每条都对应一套可证伪的判据：

| 主张 | 判据 |
| --- | --- |
| 同一批原子实体可组装出树、森林、图 | J1 |
| 池子越用越厚，新场景越来越便宜 | J2 |
| 换场景不需要改内核 | J3 |
| 通用性不依赖某个特定执行体或某套特定存储 | J4、J7 |

另有三条与"持续运营"直接相关（C3）：J5、J6、J8。

---

## 二、场景矩阵：按结构相反选，不按业务不同选

| | 场景 A | 场景 B | 场景 C |
| --- | --- | --- | --- |
| **拓扑** | **树**（单一目标） | **森林**（多目标共享同一批原子实体） | **图**（真环 + 跨目标资源冲突） |
| **形态** | 稳态控制类：某个物理量维持在设定范围 | 运营类：多个目标并行且互相依赖 | 策略类：指标自增强环、资源被多方争夺 |
| **执行体** | **机器**（无人类参与） | 人（执行事件：派发/确认/完成/前提未成立） | 人 + 机器 |
| **时间常数** | 快（毫秒~秒） | 慢（天~周） | 中（分钟级） |
| **观测** | 高频遥测 | 手工 / 导入 / 台账 | 状态导出 |
| **主要检验点** | 不依赖人、误差在本层处理、预案降级 | **复用率的答案在这里** | 环的时间延迟处理、结构缺口 |
| **优先级** | 可后置 | 先做 | 次之 |

### 2.1 为什么不用"两个相似的业务场景"

如果两个场景共享同一套词汇、同一时间常数、同一执行体类型，它们之间的相似度太高——"内核零改动"可能因为"太像"而轻松通过，测不出通用性。**通用性只能被结构差异检验。**

场景 B 与 C 的结构差异（多目标共享 vs 单目标带环）已经足够；场景 A 的价值在于**去掉人**——如果内核里隐含了"等人回复"的假设，只有无人场景能暴露它。

### 2.2 复用率的度量

```
复用率    = 本次运行需要的指标里，池子已覆盖的比例
新增组件数 = 本次需要的组件数 − 已覆盖
装配成本   = 从场景开始到图上跑通所需的人时
```

目标的形态是：场景 B 出现可观复用，场景 C 的复用率不低于 B，装配人时逐次下降。

## 三、验收判据

### J1 · 一池多用（核心）

- [ ] 同一批原子实体装配出**树**（单根、无环）、**森林**（≥3 个目标且**共享**同一批组件）、**图**（存在真环，按"读上一时间步、写下一时间步"处理，每个时间步内无环）；
- [ ] 三种形态**不引入任何新的内核概念，不给事件表加列**——形态差异全部落在事件负载里。

### J2 · 装配成本与复用率

- [ ] 逐场景记录：所需指标数 / 新增组件数 / 复用组件数 / 装配人时；
- [ ] 场景 C 的复用率不低于场景 B，装配人时逐场景下降；
- [ ] 每次组装产出**缺口清单**，缺口带位置——这是"缺口有地址"的实证。

### J3 · 内核零改动（硬验收）

- [ ] 第 2、3 个场景接入时，内核目录差异为 0 行；
- [ ] 内核代码禁用词检查零命中（词表随场景扩充，只增不改）；
- [ ] 事件表 schema 未因新场景增加任何列；
- [ ] 三个场景共用同一个内核与同一条主干分支，不设"另起一份内核"的例外。

> 第三条最容易被绕过：只要"为控制类场景加一个采样频率列"就算失败。这条约束把"内核与场景分离"变成结构上无法违反的东西。

### J4 · 不依赖人类参与

- [ ] 至少一个场景从观测到执行全链路无人类介入；
- [ ] 该场景下报告仍正常产出（接收者是上游系统而非人）；
- [ ] 执行事件在该场景中退化为机器回执，**内核不为"人"保留任何专属路径**；
- [ ] 缺口在该场景中由场景指定的外部流程闭环，不要求人类回答。

### J5 · 持续运营与逼近

- [ ] 连续运行 ≥ 20 个节拍，**不因"目标达成"而停止**；
- [ ] 产出误差随时间的曲线：误差被压入容差带并保持稳定；
- [ ] **正常运转生效**：进入容差带后主动推送显著减少，但账目与报告层照常累积；一旦突破容差带立即唤醒；
- [ ] **报告分层生效**：全部执行结果都进报告层；上报只包含缺口、预测失准、异常三类，且每条都能指出要人做哪个动作。

### J6 · 账目立得住

- [ ] **状态重建**：任取一个时刻，`最近快照 + 重放其后事件`得到的指标全集，与当时的实时值逐字段相等；
- [ ] **审计链**：任取一次方法选择，沿因果父指针上溯到最初的目标，链路完整（拆解 → 候选集 → 各候选当时账目 → 排序规则 → 实际选择）；
- [ ] **重放一致性**：同一段事件流重放两次，"当时的候选集与排序"逐字节一致；
- [ ] **断裂降级**：抽掉一条中间事件后，系统报错退出或输出降级报告，**不许静默产出错账**；
- [ ] 运行时数据库里**不存在**任何误差列或误差表。

### J7 · 存储可替换

- [ ] 玛丽对存储的依赖收敛为 RQI 的四类动作（见 03 §二）；
- [ ] 提供**两个 RQI 实现**（既定存储 + 一个桩实现），同一份玛丽定义在两个实现上产出相同行为；
- [ ] 玛丽定义与内核中**零处**直接引用既定存储的专有概念。

### J8 · 知识供给与纪律（启用语言模型时）

- [ ] 报告中的每个数字都能指回事件（脚本抽取全部数字逐个检索）；
- [ ] 语言模型不参与对账：误差由代码计算后注入；
- [ ] 提炼失败或答案不合规时上报知识缺口，不猜测；
- [ ] **对照实验**：先用固定模板产出报告建立基线，再引入模型渲染，同一批误差盲评"哪版更可决策"。结论无论正负都记录。

## 四、反指标（避免自我欺骗）

| 指标 | 红线 | 超标说明什么 |
| --- | --- | --- |
| 复用率 | 三个场景均 < 10% | **组件颗粒度错了**——比任何功能缺陷都重要 |
| 报告噪声率（推送出去但无动作 / 推送总数） | > 30% | 容差带或缺口判据失效；正常运转未生效 |
| 误差曲线 | 不收敛或持续振荡 | 时间延迟粒度或增益策略有问题 |
| 单条决策审计回放耗时 | > 30 秒 | 索引或快照策略需要调整 |
| 报告可追溯数字比例 | < 100% | 渲染层在编造 |
| 内核改动行数 | 新场景引入任何内核改动 | 分离性失效 |
| 使用方主观评价 | "这些我早知道" | 系统没有提供新信息，只是复述 |

## 五、实施路线

### P0 · 纸上装配实验（最高优先，成本最低）

**做法**：不写产品代码。用一张纸把**三个场景的图各画一遍**，只允许用 RQI 的四类动作"取知识"，给每个需要的指标写下候选组件名。

| 产出 | 通过判据 |
| --- | --- |
| 三张图（树 / 森林 / 图） | 能画出，且**共享同一批组件名** |
| 组件清单 | 标注复用与新增，给出预估复用率（J2） |
| 缺口清单 | 缺口带位置（"缺口有地址"的实证） |
| 边表 | 树的边、森林的公共节点、图的回边各有明确表达，且不新增字段 |
| RQI 需求 | 不超过四类动作；若超出，先解决耦合再编码 |
| 事件流样例 | 覆盖全部事件类型，字段够用、无需增补 |

**P0 的失败是好结果**：一天的成本换出"组件颗粒度错了"或"存储耦合过深"，比三周后才发现便宜得多。

### P1 · 账本（只做记录与投影，不接场景）

事件表、快照表、单一写入入口、三类投影（误差 / 审计链 / 方法账户）、重放器、RQI 两个实现。

**闸门**：J6 五条全过；J7 两个实现在桩数据上行为一致。

> 为什么先做账本再谈场景：**如果某件事无法在账本上表达，图怎么设计都没用。**

### P2 · 场景 B（森林）

多目标并行的运营场景接入，配置驱动。重点在**多个目标能否复用同一批原子实体**，不在场景本身好不好用。

**闸门**：J1 的树与森林两条；J2 首次给出复用率；J5 在 20 节拍上跑出误差曲线与正常运转。

### P3 · 场景 C（图）

引入真环与跨目标资源冲突（冲突生成新目标、递归拆解）。

**闸门**：J1 的图一条；**J3 三条（首个硬验收）**；J2 复用率不低于场景 B。

### P4 · 场景 A（无人参与）+ 接口收敛

引入无人类参与的场景，并把 RQI 收敛到最小方法集。

**闸门**：J4 四条；J7 三条；J8（若启用）；反指标全部在红线内。

| 阶段 | 内容 | 闸门 |
| --- | --- | --- |
| P0 | 纸上装配三张图 | 共享组件可辨识、预估复用率 > 0、RQI ≤ 四类动作 |
| P1 | 账本 + 投影 + 重放 + RQI 双实现 | J6、J7 |
| P2 | 场景 B（森林） | J1 前两条、J2、J5 |
| P3 | 场景 C（图） | J1 第三条、J3 |
| P4 | 场景 A（无人）+ 接口收敛 | J4、J7、J8 |

### 5.1 停止触发

1. **复用率过低**（三场景均 < 10%）→ 停止功能开发，回到组件颗粒度设计；
2. **J6 的重放一致性或断裂降级**无法满足 → 记录层设计重做，不做功能叠加；
3. **J3 失败**（为新场景改了内核）→ 先修分离性，再谈第三个场景；
4. **J7 失败**（RQI 膨胀到无法收敛）→ 解耦是架构前提，先解决它；
5. **J5 不收敛**且已排除知识质量原因 → 运行回路（时间粒度 / 增益 / 资源切分）需要重做。

## 六、明确不做

- 权限、多用户、多世界的完整实现（保留世界字段，不做授权界面）；
- 分析层（从轨迹自动归因）——记录体系为它预留，POC 只保证"记录是全的"；
- 主动探索（系统自己发起小范围尝试）——这是使用方的职责，永不做进系统；
- 自动组装算法——P0 到 P3 的图由配置声明，算法留到通用性验证通过之后；
- 界面——命令行加标记语言文本足够；
- 部署级监控与告警——属于运维事项，POC 只保留最原始的基岩告警；
- 性能优化；
- **场景本身的产品化**——场景只是装配实验的负载，不追求它作为业务系统好用。
