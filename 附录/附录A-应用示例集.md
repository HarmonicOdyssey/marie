# 附录 A · 应用示例集

> **本附录是示例，不是架构本体。** 它演示同一套架构在不同场景里装出来是什么样。
> 示例随时可以更换或增删，**架构文档（00–06）不依赖本附录的任何内容**。
> 选择这三个示例的唯一标准是：它们的结构尽可能不同，用来直观地检验通用性。

---

## 一、共同点与差异点

三个示例共享同一套东西（原子实体、原文层 + 知识层、组装形态、运行循环），差异只在这些地方：

| | 示例一 | 示例二 | 示例三 |
| --- | --- | --- | --- |
| 拓扑 | **森林** | **图** | **树** |
| 执行体 | 人 | 人 + 机器 | 机器 |
| 时间常数 | 天~周 | 分钟级 | 毫秒~秒 |
| 独有机制 | 执行事件与复盘 | 环的时间延迟、结构缺口 | 预案降级、无人类参与 |

**三个示例共用几个组件**（这正是通用性的直观证据）："成本""资源占用""产出"这类指标在三个场景里都出现，只是具体口径与数据源不同。

## 二、示例一：门店运营（森林 · 人执行 · 天~周）

### 目标（三个并行，共享组件）

| 目标 | 指标 | 容差带 |
| --- | --- | --- |
| 盈利 | 月利润 | 目标值 ± 容差 |
| 复购 | 复购率 | 红线：不低于某值，不可牺牲 |
| 损耗 | 损耗率 | 目标值 ± 容差 |

### 森林的样子

```
M-利润 ──┬── M-营收 ──┬── M-客流 ──┐
         │            └── M-客单价 ─┤
         └── M-成本 ──┬── M-原料    │  ← 这三个玛丽被两个目标共用
                      └── M-固定成本 │
M-复购率 ─────────────┬── M-客流 ───┘
                      └── M-会员活跃
M-损耗率 ─────────────┴── M-库存周转
```

三个目标共用客流、成本相关的同一批玛丽。为一个目标积累的账目（例如"某推广方式在某条件下带客流多少"）另一个目标可以直接用——**这就是森林的实际收益**。

### 运行特征

- **执行体是人**：每次方法执行记录执行事件（派发 / 确认 / 完成 / 前提未成立）。没有这条记录，复盘会把"没执行"误诊为"方法不灵"；
- **方法效果多维**：一次推广的效果是"客流 + 若干、现金 − 若干、客单价 − 若干"，三个维度地位平等，没有主次之分；
- **长延迟对账**：方法的预期是一条随时间变化的轨迹（第 1 周涨多少、第 2~4 周爬到多少），对账比的是轨迹，终值只是轨迹的末点；
- **横向对账**：客流与营收的变化方向不一致时，指出"至少有一本账有问题"，但不判断哪个是假的；
- **误差超容差 → 有招就自己处置，没招就报缺口**：报的是缺口，不是误差数值。使用方修正知识（确认动作），下次组装自动生效。

### 可能出现的缺口

| 缺口 | 例子 |
| --- | --- |
| 数据缺口 | 某个环节指标没有数据源 |
| 知识缺口 | 只知道"有影响"，不知道权重，且粗粒度到无法执行 |
| 结构缺口 | 所有事压在同一个人身上，拆不动 |

## 三、示例二：策略游戏中期对抗（图 · 混合执行 · 分钟级）

### 目标

第 15 分钟我方战力达到敌方的一定倍数；同时存在一条红线（关键单位不能被灭）。

### 图的样子（含真环）

```
M-战力 ──┬── M-经济 ──┬── M-资源采集 ──→ M-单位时间占用 ──┐
         │            └── M-推塔收益                      │
         └── M-经验 ──── M-参团收益                       │
                        ↑                                 │
                        └──────── M-单位时间占用 ─────────┘
                                    （环：时间被采集与参团争夺）
```

环用**时间延迟**处理：读上一时间步的占用，写下一时间步的分配，每个时间步内图无环。

### 独有机制

| 机制 | 在这里怎么体现 |
| --- | --- |
| **结构缺口** | 采集与参团争夺同一份时间。系统不排优先级，**生成新目标**"这段时间怎么分配"，递归拆解；拆不动就上报为结构缺口 |
| **降级** | 战前预编译好降级序列：正常守全部目标 → 放弃次要目标只守红线 → 保底。战中条件反射执行，不临时仲裁 |
| **资源额度来自知识** | 各层能动用多少（谁名下有几次可用、谁有多少资源池）由这个场景的知识定义，架构不规定分法。分得好，多数冲突根本不发生 |
| **快层不惊动人** | 亚秒级的判断由预编译规则承担；汇报给人只发生在战前与战后 |

### 版本变化怎么体现

一次版本更新削弱了某个收益来源时，系统**不理解版本**，它只报告"这个方法的实际效果持续低于预期"这一统计事实。要不要改预期，是使用方的动作。

## 四、示例三：稳态控制（树 · 机器执行 · 毫秒~秒）

### 目标

某个物理量维持在设定范围（例如距离、温度、液位、速率）。

### 树的样子

```
M-被控量 ──┬── M-直接观测量
           ├── M-扰动观测量
           └── M-执行器状态
```

### 独有机制

| 机制 | 在这里怎么体现 |
| --- | --- |
| **误差在本层处理** | 绝大多数误差在最低层就被处理掉，不需要向上报告——因为那一层有手段 |
| **误差越大越保守** | 观测与预期严重不符时（说明当前知识在这个局面下不可靠），缩小干预幅度、只用有实测记录的方法、拉长观察期 |
| **无人类参与** | 从观测到执行全链路没有人的环节；报告的输出对象是上游系统；缺口由场景指定的外部流程闭环 |
| **基岩兜底** | 安全相关的部分退回纯代码；报告故障的机制不依赖它自己 |

### 为什么这个示例对架构验证很重要

如果内核里隐含了"等人回复"的假设——例如把"预测未比对"当成"等人回话"，或者把执行事件当成必需——这个场景会立刻暴露它。**去掉人，是检验内核是否真的场景无关的最直接方式。**

## 五、从三个示例能看出什么

1. **同一批原子实体装出了三种拓扑**：森林（共享组件）、图（带环）、树（单链）；
2. **执行体可以是人、机器或两者混合**：执行事件在人身上必要，在机器上退化为回执，但内核不需要为此分叉；
3. **时间常数差四个数量级**（毫秒到周），靠"节拍频率按指标分档 + 时间常数分层"容纳，系统只有一套；
4. **差异全部落在配置与知识里**：指标是哪些、方法有哪些、预期是什么、容差多宽、谁是执行体——这些都不是内核的事。
