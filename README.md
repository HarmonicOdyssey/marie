# 玛丽（MARIE）架构设计备忘

> 记录一次架构讨论的背景、已达成共识的设计决策，以及待设计的开放问题。
> 日期：2026-09-07

---

## 一、背景与问题定义

### 1.1 系统定位

构建一个**目标驱动的持续决策系统**：在给定场景下，围绕一组可量化目标，反复地分配资源、执行行动、观测结果、更新认知，使场景状态尽可能逼近目标。

典型应用场景：
- 公司或组织的运营决策；
- 策略游戏中的资源调配；
- 其他"可量化目标 + 可采取行动 + 可观测结果"的持续运营类问题。

### 1.2 关键特征

- **可量化**：目标、指标、行动结果均为可量化的；
- **持续性**：系统不是一次性规划求解，而是"行动 → 观测 → 统计 → 再行动"的闭环；
- **目标易变**：现实场景（如企业经营）中目标并非一成不变，运用的场景也不尽相同，系统不应与某个固定目标或固定结构绑定。

## 二、两个例子：架构的设计哲学

在正式定义概念之前，先用两个简单的例子展示这套架构"是怎么想问题的"。它们共同体现了设计哲学：**目标逆向拆解为指标网络，每个节点只做局部推理，全局的聪明来自大量局部的、基于历史证据的决策的叠加。**

### 2.1 例一：街角咖啡店的月度利润

**目标**：让咖啡店月利润 ≥ 5 万元。

**第一步：逆向拆解**

系统从组件池中找到一个能以"月利润"为输出的玛丽，记为 M-利润。M-利润的方法集和指标依赖声明了：利润 = 营收 − 成本。于是它产生两个未知输入指标——"月营收"和"月成本"，分别触发两个新玛丽：

```
M-利润（输出：月利润）
├── M-营收（输出：月营收）
│   ├── M-客流（输出：日均客流量）
│   └── M-客单价（输出：平均客单价）
└── M-成本（输出：月成本）
    ├── M-原料（输出：原料成本）
    └── M-固定成本（输出：房租+人工）   ← 叶子：可直接观测
```

拆解到"日均客流量"时，M-客流需要"路过人数 × 进店率"。"路过人数"不可直接观测——这就是**缺口**：系统把它显式上报给用户。用户补充："店门口有闸机数据可以用"，该指标挂到数据源上，图闭合。

**第二步：单个玛丽如何做决定**

看 M-客流。数据存储里登记了三个能提升客流的方法：

| 方法 | 历史执行记录（存储中沉淀） | 成本 |
|------|--------------------------|------|
| 发传单 | 12 次，平均客流 +3%，方差大 | 低 |
| 点评平台推广 | 5 次，平均客流 +15% | 中 |
| 延长营业时间 | 2 次，平均客流 +6%，但抬高人工成本 | 中 |

M-客流读取这些历史：推广次数少但效果显著好，按探索-利用权衡（汤普森采样），它有较大概率被选；传单效果弱但便宜，作为备选。注意"延长营业时间"会推高 M-固定成本的输出——M-客流在做选择时，通过资源/副作用声明能看到这一点，或者这个冲突会浮出水面（见下一步）。

**第三步：Inference 的闭环**

- **自上而下**：月利润缺口 1.2 万 → 拆解为"营收 +1.5 万 或 成本 −0.8 万"等候选组合 → M-营收把缺口折算成"客流 +8%"下达给 M-客流；
- **选择与执行**：M-客流选了"点评平台推广"，执行；
- **自下而上**：一周后观测到账——客流 +11%，超出预期；执行结果（方法、投入、实际效果）**写回数据存储**，成为下次决策的历史；
- **下一轮**：各玛丽用更新后的观测重新评估差距。若客流达标但利润仍不足（推广费吃掉了利润），压力自然传导到 M-成本一侧——系统"自己发现"了问题该往哪使劲。

**这个例子展示的哲学**：没有中央大脑算一个总方案；每个玛丽只关心自己的输出指标、自己能用的方法、方法的历史表现；目标差距像压力一样沿图传导，观测像血液一样沿图回流，全局的协调从局部推理中涌现。

### 2.2 例二：策略游戏里的"赢下中期团战"

**目标**：第 15 分钟时我方战力 ≥ 敌方 1.2 倍。

**逆向拆解**：

```
M-战力（输出：15分钟战力）
├── M-经济（输出：金币收入）
│   ├── M-补刀（输出：补刀数）      ← 叶子：游戏API可观测
│   └── M-野区（输出：野怪收益）
└── M-经验（输出：等级）
    └── M-参团率（输出：参团时间占比）
```

**历史记录如何塑造行为**：M-经济发现存储中"速推塔"方法在最近的执行记录里收益率下降（版本更新削弱了塔皮金币）——不需要任何人告诉系统"版本变了"，历史统计的变化自动让曾经的最优方法让位。这体现了**方法与历史存于存储、组件只是其实现**的好处：数据在变，行为跟着变，架构本身不动。

**仲裁即目标的闪现**：拆解发现"打野怪"和"参团"争抢同一个资源——英雄的时间。系统没有给两者排优先级，而是生成一个新目标："第 8–12 分钟的时间分配冲突"，交给框架再拆解一次。可能分解出的方法是"调整刷野路线顺路参团"——一个**改变问题结构**的解，而不是在冲突内部委屈求全。

### 2.3 两个例子共同说明的设计原则

1. **逆向**：永远从目标出发，不知道就拆，拆不动就上报，绝不假装知道；
2. **局部**：每个玛丽只做一次"差距评估 + 方法选择"，没有全局优化器；
3. **证据驱动**：方法的地位由执行历史决定，历史变了行为就变；
4. **冲突显式化**：资源冲突变成新目标递归求解，或暴露给用户，而不是被打分机制掩盖；
5. **闭环**：观测回流、统计更新、差距重估，系统持续运转而非一次性求解。

## 三、核心概念

### 3.1 玛丽（MARIE）组件

系统的基本构件是原子化组件，命名为**玛丽（MARIE）**，由五个特性的首字母缩写而成：

| 特性 | 含义 |
|------|------|
| **M — Motivated（被激发的）** | 组件被目标（输出指标）激发而存在，没有自己的意志；闲置组件不消耗推理资源，组件池可以很大。 |
| **A — Authorizable（可授权的）** | 组件只能访问有权限访问的存储数据、采取有权限使用的方法、根据有权限知晓的历史评估方法效果。权限有三层独立粒度：数据可读性、方法可用性、历史可见性。 |
| **R — Repository-based（基于知识库的）** | 组件是数据存储中方法定义等信息的"实现/视图"；存储内容变化，实例化出的组件随之变化。 |
| **I — Inference（推理）** | 单一组件的核心是双向推理：自上而下传递拆解的目标，自下而上传递观测结果，在交汇处评估观测与目标的差距并选择要执行的方法。 |
| **E — Entity（实体）** | 组件是可命名、可引用、可组合、可复用的实体。 |

### 3.2 单个玛丽的内部结构

每个玛丽是一个"指标生产单元"，包含：

1. **输出指标**：本组件负责产出的一个（或一组）可量化指标；
2. **输入指标**：产出输出所依赖的其他可量化指标；
3. **方法（可采取的行动）**：组件可调用的行动集合，每个行动消费输入、影响输出；
4. **执行统计**：各方法历史执行结果的记录（成功率、收益分布、资源消耗等），来源于数据存储。

单个玛丽回答的问题：**"要让指标 Y 变好，我需要什么输入，有哪些手段，哪个手段历史上更有效？"**

### 3.3 三层分离的总体结构

1. **数据存储层**：方法定义 + 方法执行的历史结果，独立存在，持续沉淀，与决策架构解耦；
2. **组件（玛丽）层**：由存储中的信息实例化而来；
3. **图（玛丽森林 / 玛丽图）层**：针对某个具体目标，临时从组件池中组织出的树/DAG，问题解决后即消散。

## 四、已达成共识的设计决策

### 4.1 组件池 + 按需组装，而非常驻图

- 系统中**长期保有的是一批组件（组件池）**，而不是一个固定的图；
- 当给出一个特定目标时，从现有组件中**临时组织**出树或 DAG；图随问题解决而消散；
- 推论：
  - 图绑定目标，而目标易变，因此图本来就应该是短生命周期的；
  - 数据沉淀与推理结构解耦：执行历史持续积累，每次组装都基于最新的存储内容；
  - **没有常驻图，就没有运行中改图的一致性问题**；静态图内做推理，图与图之间通过数据存储传递变化。

### 4.2 逆向分解（backward chaining）的图构建过程

1. **起点组件**：以最终目标为输出，根据其可用方法，推导出所需输入指标；
2. **递归展开**：检查每个输入指标——
   - 若它是**可观测/现成的**（可直接测量或已有数据），该分支终止；
   - 若它是**未知的**，为它新建组件，以它为输出继续向下分解；
3. **两种终止结局**：
   - ✅ 目标被完整分解，叶子节点全是可观测指标，形成"观测 → 操作 → 目标"的完整链路；
   - ❌ 某些指标既不可观测也无法分解，系统**显式上报缺口**，请求用户补充信息或指定处理方式——"系统做不到什么"也是结构化输出。

### 4.3 图的结构形态

- 同一指标被多个组件依赖 → 树退化为 **DAG**；
- 指标间循环依赖 → 图中出现**环**；
- **有状态指标**：某组件的输出同时是它的输入（如"现金余额 = 上期余额 + 净流量"），携带跨时间步的状态。

### 4.4 时间延迟的环

- 不采用电路式的同步求解，而采用**时间延迟**：组件读取上一时间步的指标值，写入下一时间步的值；
- 好处：环从结构性问题变为时序问题——**每个时间步内图是无环的**，推理逐层传播，求解大大简化；有状态指标统一为同一模式；
- 遗留问题（时间粒度、振荡/失稳）**推迟到推理机制确定后再处理**（见 5.4）。

### 4.5 图的"动态性"的准确语义

- **在解决一个问题的过程中，图是静态的**；
- 下一次解决同样的问题时，如果数据存储中新增了方法或更新了执行结果，可能实例化出新的组件，继而组装出**不同的图**；
- 组件池是动态丰富的（随存储内容更新），图是每次按需静态组装的；
- 不存在图的"退化/剪枝"和"一致性"问题（图无常驻状态）；
- 组件的来源：根据数据存储里的信息产出。

### 4.6 资源约束：双层 + 仲裁即目标

**双层资源约束：**
- **组件级约束**：组件自身的预算/容量上限，属于局部规则，组件在选择方法时自行遵守；
- **全局资源池**：跨组件共享的资源（现金、人力、算力）。

**仲裁机制的核心决策：资源冲突的仲裁本身作为一个目标去触发。**

- 资源冲突不被优先级打分掩盖，而是被显式地变成一个**新目标**，交给同一套框架处理；
- 理由（年会例子）：当所有任务压在同一个人身上时，真正的解不是排队，而是"增加人手 / 砍掉任务 / 调整目标"这类**改变问题结构**的动作；用优先级或量化分数试图处理所有冲突必然是不对的——有些场景下所有事都必须完成，问题出在目标结构本身；
- 该设计递归复用了玛丽框架：仲裁不是架构中的特殊模块，而是一次普通的"给出目标 → 组装图 → 推理执行"；
- 若分解到底发现无可行方法，走既有的"缺口上报"通道，把问题暴露给用户——与指标无法获取的处理方式完全一致；
- **资源获取行动（如"申请预算""招聘"）也建模为组件的方法**，其执行结果同样沉淀到数据存储。

### 4.7 冷启动与执行统计

- 方法选择机制"视情况而定"，视为一个**分阶段的策略谱系**：
  1. **零数据阶段**：依赖先验——用户偏好、方法自带的声明式元数据（预期收益、成本、风险等级），或默认启发式（如先选成本最低的）；
  2. **少量数据阶段**：探索-利用权衡（如多臂老虎机 UCB / Thompson 采样），不确定性高时自动倾向探索；
  3. **数据充足阶段**：对每个方法拟合"输入状态 → 结果分布"的条件模型，选择变为给定状态下的优化问题；
- 执行统计的数据形态应**支撑不确定性估计**（次数、均值、方差/分布），使三个阶段可用同一套数据结构平滑过渡；
- **"怎么选"是一个重要但相对独立的子课题，先记录，暂缓深入**；
- 方法的**"适用条件"**（如某方法只在指标处于某区间时可用）作为候选特性纳入考虑；若引入，选择机制需先过滤"当前可选"，再决定"选哪个"。

## 五、待设计的点（开放问题清单）

### 5.1 单个玛丽的推理流程（Inference）—— 建议优先攻克

- "目标下达 → 观测上传 → 差距评估 → 方法选择"的具体流程是什么；
- 目标如何自上而下拆解传递（量化的目标值如何分摊到输入指标）；
- 观测结果如何自下而上汇聚；
- 差距评估的形式（阈值？偏差比例？效用函数？）；
- **它是所有其他问题（环、资源、统计形态）的公共地基。**

### 5.2 方法选择机制（独立子课题，暂缓）

- 三阶段策略谱系的具体实现；
- 统计数据的确切形态；
- 方法"适用条件"的表达方式与过滤机制。

### 5.3 资源仲裁的触发器

- 当多个玛丽的资源需求汇总超限时，**由谁发现冲突**并把"解决此冲突"形式化为一个新目标；
- 初步判断：这像是**框架层**（而非组件层）的职责，待设计。

### 5.4 环的推理细节（依赖 5.1）

- **时间粒度**：不同环的自然周期可能不同（现金流按天、招聘按季度），需要统一步长，还是允许指标带自己的更新频率；
- **振荡/失稳**：延迟反馈可能导致来回震荡（补货过多 → 砍单 → 缺货 → 再补货……）；运行统计能否记录此类模式，方法选择能否学会避开激进动作（可能后期才需处理）。

### 5.5 组件/方法的形式化规格

- 玛丽的完整接口定义：指标类型、方法签名、统计结构、资源声明、权限声明；
- 其他所有机制（选择、仲裁、组装）都建立在此之上。

### 5.6 图组装算法

- 给定目标和组件池，如何选择用哪些组件、走哪条分解路径（同一指标可能有多个组件能产出）；
- 组装时的冲突检测（如环的发现与标记）。

### 5.7 缺口上报与用户的交互协议

- 指标无法获取 / 无可行方法时，向用户暴露问题的形式；
- 用户补充信息后如何回流到数据存储、影响下次组装。

## 六、术语表

| 术语 | 含义 |
|------|------|
| 玛丽（MARIE） | 原子化组件，Motivated / Authorizable / Repository-based / Inference / Entity |
| 玛丽森林 / 玛丽图 | 针对特定目标从组件池临时组织出的树/DAG |
| 组件池 | 系统长期保有的组件集合，随数据存储内容动态丰富 |
| 数据存储 | 方法定义 + 方法执行历史结果的独立存储，与决策架构解耦 |
| 方法 | 组件可采取的行动，消费输入指标、影响输出指标 |
| 执行统计 | 方法历史执行结果的统计记录，支撑方法选择 |
| 逆向分解 | 从最终目标出发，逐层将未知输入指标展开为新组件输出的图构建过程 |
| 缺口上报 | 指标不可获取或无可行方法时，系统向用户显式暴露问题的机制 |
| 仲裁即目标 | 资源冲突被形式化为新目标、交给同一框架求解的设计决策 |
