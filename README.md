# 玛丽（MARIE）架构设计备忘

> 本文档记录玛丽架构的当前设计结论，随讨论持续更新。
> 最近更新：2026-09-13

---

## 一、背景与问题定义

### 1.1 系统定位

构建一个**目标驱动的持续决策系统**：在给定场景下，围绕一组可量化目标，反复地分配资源、执行行动、观测结果、更新认知，使场景状态尽可能逼近目标。

典型应用场景：
- 公司或组织的运营决策；
- 策略游戏中的资源调配；
- 其他"可量化目标 + 可采取行动 + 可观测结果"的持续运营类问题。

### 1.2 关键特征

- **可量化**：目标、指标、行动结果均为可量化的；
- **持续性**：系统不是一次性规划求解，而是"行动 → 观测 → 统计 → 再行动"的闭环；
- **目标易变**：现实场景中目标并非一成不变，运用场景也不尽相同，系统不应与某个固定目标或固定结构绑定。

## 二、两个例子：架构的设计哲学

设计哲学一句话概括：**目标逆向拆解为指标网络，每个节点只做局部推理，全局的聪明来自大量局部的、基于历史证据的决策的叠加。**

### 2.1 例一：街角咖啡店的月度利润

**目标**：让咖啡店月利润 ≥ 5 万元。

**第一步：逆向拆解**

系统从组件池中找到一个能以"月利润"为输出的玛丽，记为 M-利润。M-利润的指标依赖声明了：利润 = 营收 − 成本。于是它产生两个未知输入指标——"月营收"和"月成本"，分别触发两个新玛丽：

```
M-利润（输出：月利润）
├── M-营收（输出：月营收）
│   ├── M-客流（输出：日均客流量）
│   └── M-客单价（输出：平均客单价）
└── M-成本（输出：月成本）
    ├── M-原料（输出：原料成本）
    └── M-固定成本（输出：房租+人工）   ← 叶子：可直接观测
```

拆解到"日均客流量"时，M-客流需要"路过人数 × 进店率"。"路过人数"不可直接观测——这就是**缺口**：系统把它显式上报给用户。用户补充："店门口有闸机数据可以用"，该指标挂到数据源上，图闭合。

**第二步：单个玛丽如何做决定**

看 M-客流。数据存储里登记了三个能提升客流的方法：

| 方法 | 历史执行记录 | 成本 |
|------|--------------|------|
| 发传单 | 12 次，平均客流 +3%，方差大 | 低 |
| 点评平台推广 | 5 次，平均客流 +15% | 中 |
| 延长营业时间 | 2 次，平均客流 +6%，但抬高人工成本 | 中 |

M-客流读取这些历史：推广次数少但效果显著好，按探索-利用权衡有较大概率被选；传单效果弱但便宜，作为备选。"延长营业时间"会推高 M-固定成本的输出——M-客流在做选择时能看到这个副作用，或者该冲突会浮出水面。

**第三步：Inference 的闭环**

- **自上而下**：月利润缺口 1.2 万 → 拆解为"营收 +1.5 万 或 成本 −0.8 万"等候选组合 → M-营收把缺口折算成"客流 +8%"下达给 M-客流；
- **选择与执行**：M-客流选了"点评平台推广"，执行；
- **自下而上**：一周后观测到账——客流 +11%，超出预期；执行结果（方法、投入、实际效果）**写回数据存储**，成为下次决策的历史；
- **下一轮**：各玛丽用更新后的观测重新评估差距。若客流达标但利润仍不足（推广费吃掉了利润），压力自然传导到 M-成本一侧——系统"自己发现"了问题该往哪使劲。

**这个例子展示的哲学**：没有中央大脑算一个总方案；每个玛丽只关心自己的输出指标、自己能用的方法、方法的历史表现；目标差距像压力一样沿图传导，观测像血液一样沿图回流，全局的协调从局部推理中涌现。

### 2.2 例二：策略游戏里的"赢下中期团战"

**目标**：第 15 分钟时我方战力 ≥ 敌方 1.2 倍。

**逆向拆解**：

```
M-战力（输出：15分钟战力）
├── M-经济（输出：金币收入）
│   ├── M-补刀（输出：补刀数）      ← 叶子：游戏API可观测
│   └── M-野区（输出：野怪收益）
└── M-经验（输出：等级）
    └── M-参团率（输出：参团时间占比）
```

**历史记录如何塑造行为**：M-经济发现存储中"速推塔"方法在最近的执行记录里收益率下降（版本更新削弱了塔皮金币）——不需要任何人告诉系统"版本变了"，历史统计的变化自动让曾经的最优方法让位。这体现了**方法与历史存于存储、组件只是其实现**的好处：数据在变，行为跟着变，架构本身不动。

**仲裁即目标的体现**：拆解发现"打野怪"和"参团"争抢同一个资源——英雄的时间。系统不给两者排优先级，而是生成一个新目标："第 8–12 分钟的时间分配冲突"，交给框架再拆解一次。可能分解出的方法是"调整刷野路线顺路参团"——一个**改变问题结构**的解，而不是在冲突内部委屈求全。

### 2.3 两个例子共同说明的设计原则

1. **逆向**：永远从目标出发，不知道就拆，拆不动就上报，绝不假装知道；
2. **局部**：每个玛丽只做一次"差距评估 + 方法选择"，没有全局优化器；
3. **证据驱动**：方法的地位由执行历史决定，历史变了行为就变；
4. **冲突显式化**：资源冲突变成新目标递归求解，或暴露给用户，而不是被打分机制掩盖；
5. **闭环**：观测回流、统计更新、差距重估，系统持续运转而非一次性求解。

## 三、核心概念

### 3.1 玛丽（MARIE）组件

系统的基本构件是原子化组件，命名为**玛丽（MARIE）**，由五个特性的首字母缩写而成：

| 特性 | 含义 |
|------|------|
| **M — Motivated（被激发的）** | 组件被目标（输出指标）激发而存在，没有自己的意志；闲置组件不消耗推理资源，组件池可以很大。 |
| **A — Authorizable（可授权的）** | 组件只能访问有权限访问的存储数据、采取有权限使用的方法、根据有权限知晓的历史评估方法效果。权限有三层独立粒度：数据可读性、方法可用性、历史可见性。 |
| **R — Repository-based（基于知识库的）** | 组件是数据存储中信息的"实现/视图"；存储内容变化，实例化出的组件随之变化。 |
| **I — Inference（推理）** | 单一组件的核心是双向推理：自上而下传递拆解的目标，自下而上传递观测结果，在交汇处评估观测与目标的差距并选择要执行的方法。 |
| **E — Entity（实体）** | 组件是可命名、可引用、可组合、可复用的实体。 |

### 3.2 单个玛丽的内部结构

每个玛丽是一个"指标生产单元"，包含：

1. **输出指标**：本组件负责产出的一个（或一组）可量化指标；
2. **输入指标**：产出输出所依赖的其他可量化指标；
3. **方法（可采取的行动）**：组件可调用的行动集合，每个行动消费输入、影响输出；
4. **执行统计**：各方法历史执行结果的统计（次数、均值、方差/分布等），来源于数据存储。

单个玛丽回答的问题：**"要让指标 Y 变好，我需要什么输入，有哪些手段，哪个手段历史上更有效？"**

## 四、总体架构：本体网与两侧挂载

### 4.1 核心结构

架构的常驻核心是一张**指标/方法本体网**——指标和方法是网上的节点，彼此之间有拆解、依赖、影响关系。这张网具有**双重身份**：

```
            ┌──────────────────────────────┐
            │   指标/方法本体网              │  ← 结构化核心：可计算 + 索引双重身份
            │  节点带情态、置信度、指针        │
            └───┬───────────────────┬──────┘
       索引 ↓   │                   │   ↓ 挂接
┌───────────────────────┐   ┌───────────────────────┐
│  非结构化原文库         │   │  执行记录/观测数据       │
│ （SOP/制度/法规/台账/   │   │ （一手数据，本身是根基）  │
│   行业与管理学知识等）   │   │  聚合统计 = 时间维度压缩  │
└───────────────────────┘   └───────────────────────┘
```

- **向左，本体网是索引**：指标定义、拆解规则、方法定义、仲裁依据等信息编译自非结构化原文（管理制度/SOP、组织架构、行业/管理学/商务知识、法律法规、产品/项目信息等），节点带指针可回查原文。**原文是根基，编译产物永远可以被质疑、回查、被源文档的更新推翻**；
- **向右，本体网是骨架**：执行记录和观测数据是原生的一手数据，不是任何原文的索引；本体网为它们提供挂载的结构。聚合统计是执行记录在时间维度上的压缩形态；
- **情态字段是两个方向的汇合点**：向左要忠实于原文，向右要忠实于现实。

### 4.2 情态（modality）

节点和记录携带情态标记，区分信息的性质与来源强度：

- `declared`（先验声明）：方法/规则自称的效果，未经实测；声明还按来源分强弱（如"制度明文规定"强于"从行业知识推断"）；
- `simulated`（推演）：仿真或推演得出的结果；
- `observed`（实测）：真实执行后的观测结果，权威性最高。

原则：**实测 > 推演 > 声明**。先验与实测绝不混淆，否则证据驱动的闭环被污染。

### 4.3 双向知识流水线

非结构化世界与结构化世界之间是一条双向流水线：

- **上行（编译）**：非结构化文本 → 记忆系统提取/组织 → 产出结构化的指标定义与获取方式、拆解规则、方法定义与适用条件、统计形态建议、仲裁依据 → 写入本体网 → 组装图时被实例化为玛丽；
- **下行（沉淀）**：玛丽的执行结果、观测、决策轨迹写回存储；其中非结构化的部分（复盘报告、用户反馈等）进入原文库，成为新的知识原料；
- **闭环生长**：新知识进来 → 编译出新方法/新拆解路径 → 下次组装出不同的图。组件池因此动态丰富。

记忆系统覆盖的四个关键环节：
1. **目标该怎么拆解**——拆解规则从知识里"读"出来（如 SOP 写明交付周期受哪些环节影响）；
2. **方法执行的结果是什么**——台账、报表、复盘文档中的执行后果被识别、归因到具体方法和指标；
3. **统计的形态与选择策略**——领域知识告知"这类指标按什么周期聚合""这类决策看均值还是看尾部风险"；
4. **资源冲突怎么仲裁**——组织架构和岗位职责定义"谁有权调配什么"，规章制度定义"什么冲突必须升级"。

### 4.4 缺口上报

拆解中遇到既不可观测也无法分解的指标、或无可行方法的环节，系统**显式上报缺口**，请用户补充信息或指定处理方式。用户的回答进入原文库并建立新的本体锚点，下次同类目标不再上报。"系统做不到什么"也是结构化输出。

### 4.5 记忆分层与压缩

- **执行记录（热）→ 聚合统计（冷）**：单次执行记录随时间聚合为统计分布（次数、均值、方差等），原始记录保留可按需回查。统计就是压缩形态，原始记录就是原文指针；组件日常只读聚合层；
- **压缩降级而非随意删除**：低频访问不等于低价值（审计、复盘查的往往是冷门记录）。任何"删除级"处理仅保留元数据存根，且生命周期策略由用户授权决定，不由系统自动判定；
- **原文库同理**：压缩保留原文指针，可回查。

### 4.6 权限（Authorizable 的存储侧实现）

借鉴"多世界隔离"模型：方法定义等通用知识是共享的（基础世界），不同组织/场景/密级的执行历史与指标数据互相隔离（私有世界），玛丽按授权叠加可见范围。引用计数管理共享条目的生命周期，并支撑"源文档更新 → 派生条目失效/更新"的级联。

## 五、图的组装与运行

### 5.1 组件池 + 按需组装

- 系统长期保有的是**本体网与数据存储**，而不是固定的图；
- 给出一个特定目标时，从本体网实例化组件、临时组织出树或 DAG（玛丽森林/玛丽图），问题解决后图即消散；
- 图绑定目标，而目标易变，因此图是短生命周期的；
- 没有常驻图，就没有运行中改图的一致性问题；静态图内做推理，图与图之间通过存储传递变化。

### 5.2 逆向分解（backward chaining）

1. **起点组件**：以最终目标为输出，根据其可用方法，推导出所需输入指标；
2. **递归展开**：检查每个输入指标——可观测/现成的则分支终止，未知的则新建组件继续向下分解；
3. **两种结局**：叶子全部可观测，图闭合；或存在无法闭合的缺口，显式上报（见 4.4）。

### 5.3 图的结构形态

- 同一指标被多个组件依赖 → 树退化为 **DAG**；
- 指标间循环依赖 → 图中出现**环**；
- **有状态指标**：某组件的输出同时是它的输入（如"现金余额 = 上期余额 + 净流量"），携带跨时间步的状态。

### 5.4 时间延迟的环

- 环采用**时间延迟**处理：组件读取上一时间步的指标值，写入下一时间步的值；
- 效果：环从结构性问题变为时序问题——**每个时间步内图是无环的**，推理逐层传播；有状态指标统一为同一模式；
- 时间粒度与振荡/失稳的处理推迟到推理机制确定后解决（见 7.4）。

### 5.5 图的动态性

- 解决一个问题的过程中，图是静态的；
- 下次解决同样的问题时，若存储中新增了方法/知识或更新了执行结果，可能实例化出不同的组件、组装出不同的图；
- 组件池随存储动态丰富，图每次按需静态组装；不存在图的退化、剪枝、一致性问题。

## 六、决策与资源

### 6.1 方法选择与冷启动

方法选择是一个分阶段的策略谱系：

1. **零数据阶段**：依赖先验——用户偏好、方法的声明式元数据（预期收益、成本、风险等级，注意按情态和来源强度加权），或默认启发式；
2. **少量数据阶段**：探索-利用权衡（如 UCB / Thompson 采样），不确定性高时自动倾向探索；
3. **数据充足阶段**：对每个方法拟合"输入状态 → 结果分布"的条件模型，选择变为给定状态下的优化问题。

- 执行统计的数据形态支撑不确定性估计（次数、均值、方差/分布），使三阶段用同一套数据结构平滑过渡；
- 方法可带**适用条件**（如仅在指标处于某区间时可用）；选择机制先过滤"当前可选"，再决定"选哪个"；
- "怎么选"作为独立子课题暂缓深入（见 7.2）。

### 6.2 双层资源约束

- **组件级约束**：组件自身的预算/容量上限，属局部规则，组件选择方法时自行遵守；
- **全局资源池**：跨组件共享的资源（现金、人力、算力等）。

### 6.3 仲裁即目标

资源冲突的仲裁本身作为一个目标去触发：

- 冲突不被优先级打分掩盖，而是被显式地变成一个**新目标**，交给同一套框架逆向分解、递归求解；
- 理由：当冲突源于结构性问题（如所有任务压在同一个人/部门身上）时，真正的解是"增加人手 / 砍掉任务 / 调整目标"这类**改变问题结构**的动作；用优先级或量化分数处理所有冲突必然不对——有些场景下所有事都必须完成，问题出在目标结构本身；
- 仲裁因此不是架构中的特殊模块，而是一次普通的"给出目标 → 组装图 → 推理执行"；
- 若分解到底无可行方法，走缺口上报通道，把问题暴露给用户；
- **资源获取行动（如"申请预算""招聘"）也建模为方法**，其执行结果同样沉淀到存储；
- 仲裁依据（职责划分、升级规则等）来自本体网从组织架构与制度中编译的知识（见 4.3）。

## 七、待设计的点（开放问题清单）

### 7.1 单个玛丽的推理流程（Inference）—— 优先攻克

- "目标下达 → 观测上传 → 差距评估 → 方法选择"的具体流程；
- 量化目标值如何自上而下分摊到输入指标；
- 观测结果如何自下而上汇聚；
- 差距评估的形式（阈值？偏差比例？效用函数？）；
- 它是环、资源、统计形态等其他问题的公共地基。

### 7.2 方法选择机制（独立子课题，暂缓）

- 三阶段策略谱系的具体实现；
- 适用条件的表达方式与过滤机制。

### 7.3 资源仲裁的触发器

- 多个玛丽的资源需求汇总超限时，由谁发现冲突并把"解决此冲突"形式化为新目标；
- 初步判断：这是框架层（而非组件层）的职责。

### 7.4 环的推理细节（依赖 7.1）

- 时间粒度：统一步长，还是允许指标带自己的更新频率；
- 延迟反馈导致的振荡/失稳如何识别与规避。

### 7.5 本体网与组件的形式化规格

- 指标、方法、统计、资源声明、权限声明、情态、溯源指针的完整接口定义；
- 其他所有机制（选择、仲裁、组装）都建立在此之上。

### 7.6 图组装算法

- 给定目标与本体网，如何选择组件、选择分解路径（同一指标可能有多个组件能产出）；
- 组装时的环检测与标记。

### 7.7 编译工序的置信度与保鲜机制

- 非结构化知识 → 结构化条目的编译规则与质量控制；
- 编译产物的置信度标记（区分"制度明文"与"推断"）；
- 源文档变更时派生条目的级联失效/更新（快照 + 引用计数）；
- 关键场景中低置信度条目是否降级为缺口上报。

### 7.8 缺口上报与用户的交互协议

- 指标无法获取 / 无可行方法 / 仲裁无解时，向用户暴露问题的形式；
- 用户补充信息后如何进入原文库、建立本体锚点、影响下次组装。

## 八、术语表

| 术语 | 含义 |
|------|------|
| 玛丽（MARIE） | 原子化组件：Motivated / Authorizable / Repository-based / Inference / Entity |
| 本体网 | 指标/方法的常驻结构化网络，兼具"知识的索引"与"执行的骨架"双重身份 |
| 玛丽森林 / 玛丽图 | 针对特定目标从本体网临时组织出的树/DAG |
| 组件池 | 可由本体网实例化的组件集合，随存储内容动态丰富 |
| 原文库 | 非结构化知识（SOP/制度/法规/台账/行业知识等）的存储，本体网向左索引它 |
| 执行记录/观测数据 | 行动的原生结果数据，本体网向右挂接它；聚合统计是其时间维度压缩 |
| 情态 | 信息性质标记：`declared`（声明）/ `simulated`（推演）/ `observed`（实测） |
| 编译 | 上行工序：非结构化知识 → 结构化指标/方法/规则，产物带置信度与溯源指针 |
| 逆向分解 | 从最终目标出发逐层展开未知输入指标的图构建过程 |
| 缺口上报 | 指标不可获取或无可行方法时向用户显式暴露问题的机制 |
| 仲裁即目标 | 资源冲突被形式化为新目标、交给同一框架递归求解的设计决策 |
