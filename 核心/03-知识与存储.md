# 03 · 知识与存储

> 本篇回答：存储长什么样、玛丽怎么读它、知识怎么分类、怎么版本化与保鲜、多世界怎么隔离。

---

## 一、存储的两层

存储由两部分构成，这是**既定设计**。本篇讲怎么遵守它；**为什么是这两层、以及它和账本的分工，见 [10-认知与实践](10-认知与实践-记忆的设计.md)**。

| 层 | 内容 | 性质 |
| --- | --- | --- |
| **原文层** | 切片、规范化、去掉无意义符号后的自然语言原文 | 相对稳定；是根基 |
| **知识层** | 由原文提炼出关键概念、以及概念之间关系构成的知识图谱 | 派生；是执行依据 |

**一个前提要记住**：知识层是从文档**提炼**出来的，而提炼的产物天生是可压缩、可修订的——同一句话出现两次只记一次、计数加一。所以**它不能用来存"某一次执行"**：那类记录必须唯一、不可合并、只追加，归账本。这条边界见 10 §5.2.3。

### 1.1 两层的关系

```
      ┌──────────────── 知识层（概念 + 关系） ────────────────┐
      │                                                      │
      │  索引：每个概念、每条拆解逻辑、每个方法定义            │
      │        都带指针，能回查它出自哪份原文的哪一段          │
      └───────────────┬──────────────────────────────────────┘
                      │
      ┌───────────────┴──────────────────────────────────────┐
      │  原文层：切片、规范化后的自然语言                      │
      └──────────────────────────────────────────────────────┘
```

**一条原则**：知识层是**诠释**，原文层是**依据**。两者冲突时，以原文为准——知识层可以被质疑、回查、推翻、重编，原文不能。

### 1.2 两点纪律

1. **不论证存储的形态。** 这套存储同时服务其他检索类业务，它就是这么设计的；
2. **原文切片必须有稳定标识。** 它是所有溯源指针的落点，也是"源文变了，派生条目失效"这条机制能够工作的前提。

## 二、RQI：玛丽与存储之间的一层

### 2.1 为什么要这一层

如果玛丽直接读存储，那么"通用、可复用、可替换"立刻退化成"与这套存储绑定"。所以两者之间只隔一层薄查询接口。

**RQI（Repository Query Interface）是通用性的落点，也是本篇唯一需要冻结的接口。**

### 2.2 玛丽只需要四类动作

```typescript
interface RQI {
  // 1. 取原文切片：溯源指针的落点
  slice(ref: SliceRef): TextSlice;

  // 2. 取概念邻域：某组关键概念及其关系
  concepts(keys: ConceptKey[]): ConceptNeighborhood;

  // 3. 按指标取条目：拆解逻辑、方法定义
  entries(indicator: IndicatorRef): KnowledgeEntry[];

  // 4. 取历史账目：方法 × 适用条件 → 预期 + 样本量
  ledger(query: LedgerQuery): LedgerView;
}
```

| 动作 | 满足谁的什么需求 |
| --- | --- |
| `slice` | 审计与溯源：报告里每个数字能回查到原文哪一段 |
| `concepts` | 拆解：知道这个指标跟哪些概念相关、怎么相关 |
| `entries` | 定义：拿到拆解逻辑与方法列表 |
| `ledger` | 选择：拿到候选方法在各条件下的历史表现与样本量 |

### 2.3 《接口契约》

1. **只读。** 运行期间玛丽只能读，不能写。知识变更发生在内核之外的独立流程里；
2. **只认这四类动作。** 存储的专有概念不许出现在玛丽定义或内核代码中；
3. **返回必须带版本与情态。** 任何条目都要带它的版本标识和来源性质，否则无法做快照语义与误差判定；
4. **需要第五个动作时，这是一个信号，不是一次随意扩展。** 它意味着玛丽与存储的耦合在变深，应当先评审。

## 三、知识条目：内容分两类

| 类别 | 内容 | 用途 |
| --- | --- | --- |
| **拆解逻辑** | 指标 Y 怎么摊到它的输入指标上 | 组装与下达子目标 |
| **方法定义** | 影响指标 Y 的可执行动作，含适用条件与多维效果预期 | 选择与执行 |

方法的效果预期可以是一条随时间变化的**轨迹**，不是一个数："第 1 周 +5%，第 2~4 周爬到 +15%，之后回落"。对账方式不变，只是把"观测 vs 预期终值"变成"观测 vs 预期轨迹"，误差因此提前浮现。远期预期自带更宽的容差带——预期越远越不确定，这是诚实，不是缺陷。

### 3.1 方法定义的字段

```typescript
interface MethodDefinition {
  key: string;
  version: Version;
  applicability: Condition[];        // 适用条件：对当前状态的断言，选择前先过滤
  effects: EffectDim[];              // 多维效果：每个维度一条预期轨迹（含成本维度）
  executor: "human" | "machine" | "external";  // 执行体
  resources?: ResourceClaim[];       // 这个方法要占用什么（时间、预算、设备）
}

interface EffectDim {
  indicator: IndicatorRef;
  expectation: ExpectationCurve;     // 预期轨迹 + 各段容差带
}
```

**`executor` 这一项是本节最要紧的字段。** 它决定"执行"这个动作长什么样：

| 执行体 | 执行动作实际是什么 |
| --- | --- |
| `human` | 向某人提出一条建议（企业场景常见）。系统记录"已派发"，等观测回流 |
| `machine` | 系统自己操作（游戏、设备场景） |
| `external` | 调用一个外部系统或接口 |

架构对这三者一视同仁：**选择一个方法并执行**。所以不需要"提议通道"和"执行通道"两条路，也不需要"方案待批"这样的特殊状态——在需要人签字的场景里，"申请批准"本身就是一个 `executor: human` 的方法。

## 四、执行形态：编译态与解释态

知识条目的拆解逻辑按"能不能写成确定性规则"分两态。

| | 编译态 | 解释态 |
| --- | --- | --- |
| **形态** | 可写成代码的规则（公式、阈值、分档） | 保留自然语言的描述 |
| **执行** | 编译一次、持久化，之后确定性执行 | 每次执行时当场读取并判断 |
| **优点** | 快、便宜、行为一致 | 能承载抵抗代码化的内容 |
| **风险** | 只覆盖可以形式化的部分 | 判断可能漂移、粒度可能不足 |

### 4.1 两态可以混合

同一个玛丽的拆解可以一半是确定性规则、一半是自然语言判断。不需要强行统一。

### 4.2 解释态不是缺陷

自然语言本身就是对现实世界的一次量化与压缩（见 01 §二）。所以解释态的问题在**粒度与稳定性**，不在"能不能量化"：

- 粒度不足 → 只能做粗对账：不报"超差"，只报环比突变与趋势反转等值得关注的变化；
- 稳定性不足 → 输出必须做严格的格式校验，不合格就重试，仍不合格就降级为**知识缺口**上报，不许猜。

### 4.3 熟成

一段解释态逻辑被反复执行、行为稳定之后，可以固化成编译态。这是"从经验到制度"的路径，也是一个**需要确认的知识变更动作**——熟成不自动发生。

## 五、版本、情态与保鲜

### 5.1 情态：三种来源性质，绝不混用

| 情态 | 含义 |
| --- | --- |
| **声明** | 自称的效果，未经实测。按来源强弱再分档（明文规定强于行业推断） |
| **推演** | 仿真或推演得出的结果 |
| **实测** | 真实执行后的观测结果 |

**强度顺序：实测 > 推演 > 声明。**

**一条硬纪律**：先验与实测绝不混淆。如果把推演或声明的效果当成实测记账，整个对账体系就被污染了。冷启动阶段以声明为主是正常的，但必须标出来。

### 5.2 版本：知识只追加

- 修改知识 = **追加新版本**，旧版本永久保留；
- 引用知识的方式永远是 **key + version**，不是"当前最新"；
- **未比对的预测按生成时绑定的版本对账**（快照语义），不追溯、不重算；
- 新组装使用最新版本。

"历史账目在知识修正后怎么办"因此不构成问题：**换版本重跑投影即可，原始记录不动。**

### 5.3 版本管理的实现建议

不自己造版本表。让知识以文件形式存放并纳入版本控制，事件里只记录 `{key}@{版本标识}`。这样版本历史、差异比对、回滚全部复用现成工具。

### 5.4 保鲜：源变则派生失效

| 机制 | 说明 |
| --- | --- |
| **溯源指针** | 每条派生条目都指向原文切片的具体位置 |
| **级联失效** | 源文变更后，所有派生自它的条目自动失效，需重新编制 |
| **置信度** | 派生条目带置信度，低置信度条目在方法选择中降权，必要时降级为缺口 |
| **引用计数** | 共享条目的生命周期由引用计数管理，被引用时不删除 |

原文层更新后，知识层**结构性失效**，不需要人工检查有没有受影响——这是把溯源指针做成硬性要求的原因。

## 六、多世界隔离

| 世界 | 内容 |
| --- | --- |
| **共享世界** | 通用知识、通用方法定义 |
| **私有世界** | 各对象（门店、部门、势力、设备组）的账目与私有方法 |

玛丽按授权把多个世界**叠加**成她能看到的那一个视图（见 02 §三）。几点后果：

- **私有到共享的晋升**：某个对象验证有效的私有方法经授权晋升到共享世界，就变成所有对象可用的方法。组织学习的技术形态，就是账目与经验从私有世界向共享世界的晋升；
- **事实的不可变性不受世界划分影响**：无论哪个世界，事实只追加；
- **训练数据集的抽取本身是一次授权查询**：它受同样的多世界规则约束，不是一条单独的通道。
