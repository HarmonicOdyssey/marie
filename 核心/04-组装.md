# 04 · 组装

> 本篇回答：从池子到一张可运行的图，中间发生了什么——盘点、拆解、连接、缺口、告警。
> 运行（节拍、心跳、状态）见 05。记录与回放见 05 §五。

---

## 一、组装是什么

**组装 = 从池子里挑出本次运行需要的玛丽，连成一张图，并给出缺口清单。**

组装不执行任何业务逻辑，也不产生任何业务结论。它的产出只有两样：

| 产物 | 用途 | 生命周期 |
| --- | --- | --- |
| **组件图** | 本次运行 | 一次运行结束即解散 |
| **缺口清单** | 池子生长的方向标 | 永久留存，被补齐后成为池子资产 |

组装是**只读知识**的：它读存储、读池子，不改任何东西。修改发生在知识修改流程里。

---

## 二、两条组装原则

### 2.1 逆向：从目标出发倒着拆

组装从顶层目标开始，按拆解逻辑展开它需要的输入指标，递归下去，直到：

- 每个末端指标**可直接观测** → 图闭合；
- 某处**拆不动** → 缺口上报，不许静默跳过，也不许用看似合理的值填充。

### 2.2 复用优先：先问池子里有没有

展开一个输入指标时，顺序是固定的：

1. 池子里**已有**能产出该指标的玛丽 → 直接复用，连边；
2. 池子里没有，但它**可直接观测** → 作为叶子节点；
3. 两者都不成立 → **组件缺口**，记录位置。

这条顺序不能颠倒。先造新的再去重，等于放弃了池子的全部价值。

## 三、三种形态

同一批原子实体可以装出三种结构。它们的差异**全部落在边的负载与节点的目标归属上，不需要新的概念、新的字段**。

| 形态 | 结构 | 出现条件 |
| --- | --- | --- |
| **玛丽树** | 单根、无环、单一目标 | 一个目标 |
| **玛丽森林** | 多棵树共享同一批原子实体 | 多个目标并行 |
| **玛丽图** | 存在共享节点、环，或跨目标依赖 | 指标互相影响、资源被多方争夺 |

### 3.1 森林的判定标准是"共享"

多个目标各装一棵互不相干的树，那是三棵树，不是森林。**森林的判定标准是：不同目标的树之间共用同一批原子实体。**

咖啡店的三个目标——利润、复购、损耗——都依赖客流与成本，因此共用同一批玛丽。它带来的实际好处是：为一个目标积累的账目，另一个目标可以直接用。

### 3.2 图里的环：用时间延迟处理

指标之间有循环依赖（甲依赖乙、乙依赖甲），或者指标依赖自己（"本期余额 = 上期余额 + 净流量"），统一采用**时间延迟**：

> **读上一时间步的值，写下一时间步的值。于是每个时间步内的图无环。**

这条规则让推理可以逐层传播，也把"有状态指标"统一成同一种东西——它的状态就是上一时间步的自己。所有带记忆的指标都是同一个模式，不需要为它们设计专门的机制。

**要留意的**是延迟反馈带来的振荡：动作生效有延迟时，纠偏动作可能叠加过头，误差来回摆动。识别与处理见 05 §四（误差越大动作越保守）与 06（争议与取舍）。

### 3.3 跨目标的资源冲突：结构缺口

当多个目标争夺同一份有限资源（同一个人的时间、同一笔预算、同一台设备）时，系统的做法不是打分排序，而是：

> **把冲突本身变成一个目标，交给同一套框架递归拆解。**

理由：冲突真正需要的解往往是**改变问题结构**（加人、砍范围、外包、改目标），在冲突内部委曲求全拿不到这种解。打分排序恰好把这个结构性信息吞掉了。

三条配套约定：

- 资源获取动作（申请预算、招聘、采购）本身也是**方法**，执行记录照常入账；
- 仲裁的产物（如新增的编制、新签的合同）沉淀为池子的永久资产；
- 拆不动就上报——**结构缺口**。暴露问题本身就是输出。

**资源怎么分、额度怎么定，属于知识，不属于架构。** 不同组织的预算制度、工时安排办法各不相同，没有通用解法。系统的职责是按知识库里的规则执行；知识覆盖不到的地方，走结构缺口或知识缺口上报。架构不为它设计专门机制。

## 四、缺口：五类，都带位置

| 缺口 | 含义 | 归属 |
| --- | --- | --- |
| **数据缺口** | 指标既不可观测也无法分解 | 需要接入数据源 |
| **知识缺口** | 拆解逻辑缺失，或只有无法执行的粗粒度描述 | 需要补知识 |
| **方法缺口** | 某环节没有任何可行方法 | 需要补方法 |
| **组件缺口** | 组装时发现这个位置缺一个玛丽 | 最精确的形态，直接指向池子该长什么 |
| **结构缺口** | 资源冲突无解 | 需要改变问题结构 |

四条纪律：

1. **必须带位置**。缺口要写成"在这个指标的这一步做不了"，不能写成"这个目标做不了"；
2. **不许降级为静默**。宁可上报也不能猜；
3. **上报即入账**。缺口清单永久留存，被补齐后下次同类目标不再上报；
4. **无人场景中缺口不能靠人类回答闭环**，由场景指定的外部流程处理（见 07 §三）。

## 五、组装产出的健康指标

组装过程顺手算得出几个数字，它们是**系统对自身记账**的一部分，用来回答"这份判断值多少信任"：

| 指标 | 含义 |
| --- | --- |
| **覆盖率 / 复用率** | 本次需要的指标里，池子已覆盖的比例 |
| **指标可观测率** | 末端指标里有观测来源的比例 |
| **账目厚度** | 每条预期背后的实测样本量 |
| **实测占比** | 账目里实测情态相对声明情态的比例 |

这些数字应当能随时呈现给使用方：看到"这条判断基于 3 次实测"，就知道该信它几分。它同时也是冷启动阶段何时结束的判据。

## 六、组装算法的现状

**复用匹配与环检测是成熟问题，不需重新设计。** 目前明确的是原则（复用优先、逆向、环用时间延迟）与产出（图 + 缺口清单），未定的是两处细节：

| 问题 | 兜底 |
| --- | --- |
| 同一指标有多个玛丽能产出时选谁 | 使用方偏好，或上报为缺口由人指定 |
| 复用匹配的相似度如何判定 | 以指标引用为准；指标元数据规范化是前置工作 |

**指标词汇的规范化是必须先做的前置工作**：同义异名（"客流 / 客流量 / 到店人数"）与同形不同义（"完成度"在不同场景中指不同的量）会直接导致复用失败或错误复用。这件事不做，池子再厚也接不上。
