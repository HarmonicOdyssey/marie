# 10 · 认知与实践：记忆的完整设计

> 本篇从设计哲学推到底层数据结构，**假定读者没有任何背景知识**。
> 它回答一个问题：**一个需要持续做决策的系统，它的"记忆"该怎么存。**
> 读完你应该能明白：为什么需要两种存储、它们各存什么、字段为什么这么设计、以及怎么验证做对了。

---

## 一、为什么记忆是这个系统的核心问题

### 1.1 一个系统要持续做事，必须先能记住事

假设你雇一个人管门店，但他每天早上醒来就忘掉昨天的一切——他还能干活吗？

不能。他不知道上周的促销有没有效果、不知道哪个供应商靠谱、不知道上个月为什么亏了。他每天都会从零开始，把同样的错再犯一次。

**记忆不是辅助功能，它是"能持续做对事"的前提。** 因为"做对"这件事本身就是从过去的结果里学来的。

### 1.2 更麻烦的是：记忆有两种用法，要求正好相反

同一个人的记忆，被用在两件要求完全相反的事情上：

| 用法 | 例子 | 对记忆的要求 |
|---|---|---|
| **支持判断** | "这类促销在雨天大概能带多少客流？" | 需要**概括**。具体是哪天做的、几点做的，都不重要，重要的是规律 |
| **接受审计** | "上周二为什么决定投那笔钱？" | 需要**精确**。当时依据的是哪份文件、哪个版本、谁批的，一个字都不能错 |

一件事要求把细节磨掉只留规律，另一件事要求细节一个字都不能丢。**这就是整个设计最根本的张力。** 后面所有的结构，都是为了同时满足这两件事。

### 1.3 所以先要回答：知识和记忆是同一种东西吗

这不是哲学思辨，它决定你该建一套存储还是两套。

---

## 二、人脑给的三个答案

### 2.1 同一套基质

人脑里没有"知识区"和"记忆区"。神经元和突触构成的网络里，**语义知识（"巴黎是法国首都"）和情景记忆（"昨天我去了书店"）是同一种东西——都是突触连接强度的分布模式**。

所以第一层答案：**是同一类东西，不是两类。**

但只说到这里会得出错误结论。还有两条同样重要。

### 2.2 有种类之分，分的是"怎么取"，不是"存在哪"

心理学把长时记忆分了类：

| 类别 | 内容 | 特点 |
|---|---|---|
| **内隐记忆** | 骑车、游泳、打字 | 说不出来，但身体会 |
| **外显 · 语义** | 事实、概念、规律 | 能说出来，与具体时间地点无关 |
| **外显 · 情景** | 亲身经历的具体事件 | 能说出来，绑定时间地点 |

关键的区分不是"存在大脑哪个部位"，而是**提取方式**：语义记忆靠概念线索取（"促销"→ 想起一堆促销规律），情景记忆靠时间地点线索取（"上周二"→ 想起那天的事）。

**同一个网络，两套索引。**

### 2.3 有一个方向：情景会变成语义

这是最重要的一条。

你经历过一百次"下雨天客人少"，慢慢地你不再记得任何一次具体的下雨天，但你**知道**"下雨天客人少"。这个过程叫**巩固（consolidation）**：白天经历的具体事件，在海马体里快速记下；睡眠中大脑把这些事件**重放**很多遍，从中抽出规律，写进皮层成为语义知识，具体细节脱落。

> **知识是记忆被压缩、抽象之后的样子。**

不是两种东西，是**同一份东西的两个加工阶段**。

而且这个加工**不是在经历当时完成的**——它需要时间（睡眠、离线重放）。白天你只是记下事件，规律是后来才浮现的。

### 2.4 反过来，认知也影响记忆

你已有的知识框架决定你注意到什么、记住什么。一个老手看现场，看到的细节和新手完全不同——因为他的语义框架在替他筛选。

这就是"认知与实践相互作用"的神经学对应物：**实践产生记忆 → 记忆压缩成认知 → 认知筛选下一轮实践。**

## 三、从脑科学到设计：真正的分歧在"写入纪律"

### 3.1 先定义两种性质

把上面三条翻译成工程语言，会发现记忆里的东西分成两种**性质**：

| | **可压缩的** | **不可压缩的** |
|---|---|---|
| 同一件事再发生 | 合并进已有的，计数加一 | 新增一条，旧的绝不动 |
| 能否修改 | 能（发现记错了就改，或出新版本） | 不能（记错了只能再写一条更正） |
| 生命周期 | 会衰减、会失效、会被删 | 永不删除 |
| 回答的问题 | "世界通常是什么样的" | "当时究竟发生了什么" |
| 脑内对应 | 语义知识（皮层） | 情景记忆（海马体，未巩固的） |

**这两种性质不能混在同一张表里。** 一旦混了，"同一件事发生两次"这个信息就丢了——要么被合并成一次（审计失效），要么变成两条互不相干的记录（规律提不出来）。

### 3.2 由此得到的第一个结论：结构可以同，纪律必须分

注意我上一节说的是"同一套基质"。工程上的对应是：

- **数据结构可以完全一样**——同样是"节点 + 关系"，同样的类型定义，同样的查询方式；
- **写入纪律必须分开**——一块只追加，一块可修订。

这不是折中。**人脑就是这么做的**：同一套突触，巩固机制决定哪些痕迹被合并、哪些被保留为具体情节。

> 一句话：**分歧不在结构，在纪律。**

### 3.3 顺带排除一个错误做法

有人会想："既然知识不可压缩、实例可压缩，那我给数据结构加一个'实例'类型不就行了？"

不行。因为问题不在类型够不够，**在合并策略**。同一个类型下，如果写入时仍然合并计数，加了实例类型也没用；如果不合并，那它就已经不是"可压缩"的那一块了。

**该分的是层，不是类型。**

## 四、完整设计

### 4.1 总体形状

```
                 实践（只追加）
               ┌──────────────┐
               │   事件账本     │  "当时究竟发生了什么"
               └──────┬───────┘
                      │
         ①巩固：从轨迹里聚合出规律
                      │
                      ▼
               ┌──────────────┐
               │    认知层     │  "世界通常是什么样的"
               │  （可修订）    │
               └──────┬───────┘
                      │
         ②反馈：认知产出预期，预期决定怎么实践
                      │
                      └──────────→ 回到实践

   外部文档（SOP/制度/手册）──③提炼──→ 认知层
```

三个通道，缺一不可：

| 通道 | 方向 | 作用 |
|---|---|---|
| **① 巩固** | 实践 → 认知 | 从自己的经历里抽出规律 |
| **② 反馈** | 认知 → 实践 | 用规律指导下一轮行动 |
| **③ 提炼** | 文档 → 认知 | 吸收别人已有的经验 |

**通道③是必需的、也是玛丽存在的理由之一**：一个组织几十年的经验大量写在文档里（SOP、制度、手册），系统读不到"别人脑子里的实践"，只能读文本。所以企业场景必须有文本这一路。

**通道①②构成闭环。** 这个环一旦断掉，系统就退化成两个互不相干的数据库——有知识但不长进，或有记录但不用。

### 4.2 实践层：事件账本

#### 4.2.1 核心对象是"事件"

**事件 = 在世界里发生的一件事。**

它可以是系统自己做的（发起一次方法），也可以是世界发生的（竞争对手开业、下雨、政策变化）。两者记在**同一条时间线上**，这一点后面第五节会说明为什么重要。

一条事件包含：

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `id` | 自增序号 | **顺序**。账本的第几条，是唯一可靠的先后依据 |
| `tick` | 业务时间（"这件事发生在世界的哪个时刻"） | 补录、倒序到达时，业务时间与入账时间会不一致 |
| `recorded_at` | 入账时间（"这条记录是什么时候写进来的"） | 区分"当时不知道"与"后来才知道" |
| `type` | 事件类型 | 见 4.2.2 |
| `caused_by` | **因果父指针** | 见 4.2.3 |
| `knowledge_ref` | 本条依据的知识版本 | 见 4.2.4 |
| `snapshot_id` | 锚定的快照 | 见 4.2.5 |
| `payload` | 具体内容（JSON，各类型自定义） | 保证主结构不随场景变化 |
| `world` | 世界标记 | 多租户隔离 |

#### 4.2.2 事件类型

| 类型 | 记的是 |
|---|---|
| 目标下达 | 谁下了什么目标（指标、目标值、容差带、期限） |
| 拆解 | 目标被拆成了哪些子目标 |
| 方法选择 | 当时有哪些候选、各自的依据、选了谁 |
| **预测** | 发起一个方法时，预期会产生什么结果、观察期多长 |
| **执行事件** | 方法执行到哪一步了（已派发 / 已确认 / 已完成 / 前提未成立） |
| 观测 | 实测到某个指标的某个值 |
| 环境事件 | 世界上发生的、非系统引发的事 |
| 报告 | 系统向人报告了什么 |
| 知识变更 | 知识被改动了（旧版本 → 新版本） |
| 心跳发现 | "本该发生但没发生"（预测到期未观测、数据源静默） |

#### 4.2.3 因果父指针：让"为什么"可以被追

**因果父指针 = 每条事件记录里，一个指向"我为什么发生"的字段。**

比如：

```
目标下达（"里程碑按期率 ≥ 90%"）
   ↑ caused_by
拆解（"拆成三个里程碑"）
   ↑ caused_by
方法选择（"在三个候选里选了提醒负责人"）
   ↑ caused_by
预测（"预期 3 天内有进展"）
   ↑ caused_by
执行事件（"已派发"）
```

从任何一条往上走，都能走到最初的目标。**这就是"审计"的技术实现**：问"当时为什么这么选"，答案就是这条链。

**为什么必须有这个字段**：如果没有它，账本只是一堆按时间排列的散事，没法回答"为什么"。而"决策可审计"是这套东西存在的前提之一。

#### 4.2.4 知识版本引用：让"当时依据什么"可查

`knowledge_ref` 记的是"做出这个决策时，依据的是哪一版知识"，形如 `方法key@版本号`。

因为 4.3 节会讲，知识是**可修订**的——同一个方法定义今天和三个月前可能不一样。如果不记版本，回头看三个月前的决策，你会用今天的知识去解释它，那是错的。

**配套的一条规则**：预测按**生成时**绑定的版本对账，不追溯。知识后来改了，历史账目不变。

#### 4.2.5 快照：让重放不必从开头跑

**快照 = 在某一时刻，把所有指标的当前值整体拍一张照片存下来。**

为什么需要：账本会越来越长。如果要看第 9000 条时的世界状态，难道要从第 1 条重放 8999 条？

快照解决了这个：**任意时刻的状态 = 最近的一个快照 + 从它往后重放事件。**

```
事件 1 ── 事件 2 ── ... ── 事件 5000 ── [快照 A]
                                          │
事件 5001 ── ... ── 事件 9000 ←──────────┘
                              ↑
                    看第 9000 条状态 = 快照A + 重放 5001~9000
```

**快照的频率是纯性能参数**，不影响表达能力——存得越密，重放越快，占的地方越多。

#### 4.2.6 三条写入铁律

| 铁律 | 含义 | 违反了会怎样 |
|---|---|---|
| **只追加** | 记录只有"新增"，没有"修改"和"删除" | 审计失效——你不知道看到的是原始记录还是被改过的 |
| **误差不落库** | 记录里只存**事实**（观测值、预期值），"误差"每次现算 | 知识修正后，历史误差无法按新知识重算 |
| **单一写入入口** | 全系统只有一个函数能写账本 | 并发写入打乱 `id` 顺序，而顺序是重放的前提 |

第二条值得展开：**为什么"误差"不能存？**

误差 = 观测值 − 预期值。两者都是事实，都可以存。但误差是**算出来的**。如果存下来，那么当知识被修正（"预期本来应该是 +15%，不是 +10%"），历史误差就没法重算了——因为库里存的是当时用 +10% 算出的旧数。

而如果只存事实、误差每次现算，知识一改，重跑一遍投影，所有历史误差都按新知识重算。**这就是"账目永远可以重算"的代价与收益。**

### 4.3 认知层：可修订的知识

#### 4.3.1 它存什么

认知层回答"世界通常是什么样的"，内容包括：

- **指标**（客流、成本、按期率……）；
- **方法**（提醒负责人、发传单、调整排期……），含适用条件与预期效果；
- **拆解逻辑**（利润怎么拆成营收和成本）；
- **概念之间的关系**（因果、组成、同义）。

#### 4.3.2 认知层的两条来源

| 来源 | 通道 | 特点 |
|---|---|---|
| **外部文档** | ③提炼 | 别人过去实践的压缩。带原文出处，可回查 |
| **自己的实践** | ①巩固 | 自己轨迹的压缩。靠统计聚合得出 |

两者最终都变成同一种东西：**关于世界的一般性判断**。

#### 4.3.3 知识必须可修订，而且要留版本

知识会错、会过时。所以认知层的关键机制是：

- **修改 = 追加新版本**，旧版本永久保留（不可覆盖）；
- 引用知识永远用 `key + 版本`，而不是"最新版"；
- 源文档变了，从它提炼出的条目**自动失效**，需要重新提炼。

**为什么旧版本必须留**：审计要求。三个月前的决策依据的是旧版本，如果旧版本被覆盖，那条决策就永远解释不清了。

### 4.4 两层如何连接

不需要新的数据结构——**靠两个引用**：

| 引用 | 从哪到哪 | 作用 |
|---|---|---|
| **方法 key** | 账本的预测事件 → 认知层的方法定义 | 这次执行的是哪个方法 |
| **事件 id** | 认知层的聚合统计 → 账本的原始事件 | 这条统计是从哪些事件算出来的 |

**关键点**：认知层里**不存"某一次执行"**。执行实例只在账本里。认知层只存方法定义和聚合后的统计。

这样避免了一个大坑：认知层是"合并计数"的（同一件事发生两次只记一个节点、计数加一），如果执行实例也放进去，两次不同的执行会被合并成一次，账目就废了。

## 五、具体数据结构

### 5.1 实践层：账本

```sql
CREATE TABLE events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,  -- 序号即顺序
  tick          TEXT NOT NULL,      -- 业务时间
  recorded_at   TEXT NOT NULL,      -- 入账时间
  world         TEXT NOT NULL DEFAULT 'main',
  type          TEXT NOT NULL,      -- 事件类型
  caused_by     INTEGER,            -- 因果父指针，可空
  snapshot_id   INTEGER,            -- 锚定快照，可空
  knowledge_ref TEXT,               -- {方法key}@{版本}
  payload       TEXT NOT NULL       -- JSON，各类型自定义
);

CREATE TABLE snapshots (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  tick     TEXT NOT NULL,
  taken_at TEXT NOT NULL,
  world    TEXT NOT NULL DEFAULT 'main',
  payload  TEXT NOT NULL            -- JSON：全部指标的当前值
);
```

两条约定：

- **事件表上建只追加约束**：用数据库触发器拒绝任何 UPDATE 和 DELETE。不靠约定，靠数据库；
- **`payload` 是自由 JSON**：场景特有的内容全挂在这里，所以**事件表永远不因新场景加列**。

`payload` 的几种典型形状：

```jsonc
// 预测：发起一个方法时冻结的预期
{ "method": "提醒负责人", "method_version": 3,
  "expectation": [{ "offset": "3d", "expected": 0.2, "tolerance": [-0.05, 0.05] }],
  "window": { "from": "2026-03-05", "to": "2026-03-08" } }

// 执行事件
{ "prediction_id": 4711, "status": "已派发" }

// 观测：这里存的必须是**结构化的数值**，不是文本
{ "indicator": "里程碑按期率", "value": 0.88, "modality": "observed", "source": "daily_report" }
```

**最后这条很关键**：数值必须是数字，不能是"客流涨了 11%"这样的文本。因为账本要对账——做减法、比容差带、画曲线。文本做不了这些。

### 5.2 认知层：知识图谱

认知层是一张图：**节点**表示概念，**边**表示关系。

#### 5.2.1 六种节点类型

| 类型 | 名称 | 存什么 | 例子 |
|---|---|---|---|
| `g` | 普遍概念 | 事物的类别，不特指 | 服务器、促销活动、里程碑 |
| `s` | 单独概念 | 特指的一个个体 | Server-001、张三、前置防撞包 |
| `t` | 时间 | 明确的时间点/段 | 2024年、今年元旦 |
| `l` | 位置 | 明确的地点/范围 | 北京、3号仓库 |
| `f` | **事实** | 行为动作、状态变化、属性、关系、示例 | 服务启动、客流下降、前置防撞包检测到障碍物 |
| `r` | 非文本资源 | 代码块、图片、表格 | 架构图、一段代码 |

**注意 `f` 的范围很宽**：它不只是"陈述句"，而是**一切关于世界发生了什么/是什么的断言**。这是这套设计的核心选择——**放弃细分"类型"，把细节全部打包进事实的文本里**。

这样做的好处（这是它的设计动机）：如果允许 LLM 自由发明关系类型（"导致"、"引起"、"触发"、"使得"……），边类型会无限膨胀，图谱就无法用于确定性计算和推理了。把关系收敛到固定的几种，把细节留在文本里，**抽取的稳定性大幅提高**。

#### 5.2.2 六种关系

| ID | 名称 | 从 → 到 | 语义 |
|---|---|---|---|
| 1 | 实例 | 单独概念 → 普遍概念 | Server-001 是 服务器 |
| 2 | 是 | 概念 → 概念 | LLM 是 大语言模型（同义/同一实体） |
| 3 | 属于 | 概念 → 概念 | 车轮 属于 汽车（部件） |
| 11 | 参与 | 概念 → 事实 | 张三 参与 张三完成了任务 |
| 12 | 发生 | 事实 → 时间/位置 | 服务启动 发生 2024年 |
| 13 | 导致 | 事实 → 事实 | 内存溢出 导致 服务宕机 |

**ID 21-100 是预留区**，供将来新增（例如企业专属的关系类型）。

#### 5.2.3 Fact 的合并计数：本节最需要讲清的地方

每个节点（和每条边）带两个计数字段：

| 字段 | 含义 |
|---|---|
| `occurrence_count` | 它在所有文档里一共出现了多少次（聚合） |
| `world_occurrence_stats` | 按世界分槽：`{"Base": 10, "CorpA": 3}` |

**机制**：同一句话再次出现时，**不新建节点**，只是把对应节点的 `occurrence_count` 加一。

举例："内存溢出导致服务宕机"这句话在 3 份文档里都出现过，那么：
- "内存溢出"节点：`occurrence_count = 3`（如果之前没有，则新建，计数为 1）；
- "服务宕机"节点：`occurrence_count = 3`；
- 它们之间那条"导致"边：`occurrence_count = 3`。

**为什么要这么设计**：这样"高频事件"天然聚成了一个社区——`occurrence_count` 高的节点就是热点，不需要跑昂贵的图聚类算法。而且查"这个现象历史上出现过几次"直接读计数就行。

**这正是它不能用来存执行实例的原因**：

> 认知层的 Fact 表达的是"**这件事发生过 N 次**"，不是"**第 N 次发生的那个瞬间**"。
> 如果拿它存执行记录，3 月 5 日那次和 3 月 12 日那次会被合并成一个节点、计数变成 2——**审计要的"那一次"就永远找不回来了。**

#### 5.2.4 快照在这里是另一种东西（别和账本的快照混了）

**同名不同物**，这一点很容易搞错：

| | 账本的快照（4.2.5） | 认知层的快照 |
|---|---|---|
| 是什么 | 某一时刻全部指标的当前值 | **一次文档入库所产生/改动的全部节点与边的清单** |
| 干什么用 | 加速重放 | **支持增量更新与清理** |
| 怎么用 | 读状态时当起点 | 文档被修改时，按这个清单把不再出现的节点计数减一，减到 0 就删掉 |

**认知层的快照解决什么问题**：文档改了，之前从旧版文档提取的、现在不再出现的内容要清理掉。但你不能全表扫描去找——所以入库时就把"这次都动了哪些节点和边"记成本地文件。文档更新时加载这个文件，**精确地**只把受影响的计数减回去，孤立节点自然归零被删。

这样图谱不会被过期内容污染，也不会误删被其他文档共享的概念（因为计数没归零）。

#### 5.2.5 数值在认知层里是文本（这是它的边界）

认知层里没有"数值"这种节点类型。**指标的值是被写进事实的文本描述里的**。

举例：文档里一句"当障碍物距离小于 2 米时触发紧急制动"，抽取结果里 `2米` 会被当成一个**单独概念**（一个特指的实体），而不是一个可运算的数字。

**这对认知层没问题**（它要的是检索和因果溯源），但**对账本不行**。所以：

| 谁需要数值运算 | 从哪取 |
|---|---|
| 对账（观测 vs 预期）、比容差带、画误差曲线 | **账本**（观测事件里存的是结构化数字） |
| 检索、溯源、看规律 | 认知层 |

这就是两层分工的一个具体体现，也是 4.4 节"靠方法 key 和事件 id 连接"的实际含义。

## 六、一条红线与四条验收

### 6.1 红线

> **实践层只追加、永不修改、永不合并。**

这条一旦破了，整套东西的意义就没了——审计失效、时序失效、序列学习失效。

**它在实现上必须是机械保证**：数据库层面的触发器拒绝 UPDATE/DELETE，而不是靠开发者自觉。

### 6.2 四条验收（都可机械检查）

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | **事件改不了** | 直接对事件表执行 UPDATE 和 DELETE，必须被数据库拒绝 |
| 2 | **重放只读** | 重放前后比对账本行数与文件哈希，必须完全一致 |
| 3 | **状态能重建** | 任取一个时刻，`最近快照 + 重放其后事件` 得到的状态，与当时的实时值逐字段相等 |
| 4 | **能追因果** | 任取一条事件，沿因果父指针上溯，必须能走到最初的目标；链路断了必须显式报错，不许静默返回半条链 |

再加一条属于认知层的：

| 5 | **知识改了历史不变** | 把某个方法的预期从 +10% 改成 +15%，已发生的预测仍按 +10% 对账，新预测才用 +15% |

## 七、这套设计解决了什么

回到第一节提出的那对矛盾：

| 需求 | 由谁满足 |
|---|---|
| 支持判断（要概括） | 认知层：合并计数、聚合统计 |
| 接受审计（要精确） | 实践层：只追加、因果父指针、知识版本引用 |

以及第一节问的"知识和记忆是不是同一种"：

| 层面 | 答案 |
|---|---|
| 数据结构 | **同一种**（节点 + 关系 + 计数） |
| 写入纪律 | **两种**（合并 vs 只追加） |
| 关系 | 认知是从实践**巩固**来的；认知又通过**预测**反馈回实践 |

**最精简的表述：**

> 一套结构，两种纪律，三条通道（巩固 / 反馈 / 提炼），一条红线（账本只追加）。

## 八、术语速查

| 术语 | 一句话解释 |
|---|---|
| **实践层 / 账本** | 只追加的事件记录。"当时究竟发生了什么" |
| **认知层 / 知识层** | 可修订的知识图谱。"世界通常是什么样的" |
| **事件** | 世界里发生的一件事，账本的一行 |
| **快照（账本）** | 某一时刻全部指标值的照片，用于加速重放 |
| **快照（认知层）** | 一次文档入库动了哪些节点和边的清单，用于增量更新与清理 |
| **因果父指针** | 事件里指向"我为什么发生"的字段，靠它把"为什么"追出来 |
| **知识版本引用** | 事件里记下"当时依据的是哪一版知识" |
| **只追加** | 只能新增，不能修改和删除 |
| **合并计数** | 同一事实再出现时只把计数加一，不新建节点 |
| **occurrence_count** | 一个节点/边在所有文档里出现的总次数 |
| **world_occurrence_stats** | 上述计数按"世界"分槽后的明细 |
| **巩固** | 从实践记录里聚合出认知（规律）的过程 |
| **反馈** | 认知产出预期，预期决定下一轮实践 |
| **提炼** | 从外部文档抽出结构化认知 |
| **情态** | 信息的来源性质：声明（人说的）/ 推演（算出来的）/ 实测（真发生的） |
| **投影** | 不属于两类存储、每次现算出来的视图（误差、审计链、聚合统计） |
| **误差不落库** | 只存事实，误差每次现算——这样知识改了历史误差还能重算 |
