# 05 · 运行

> 本篇回答：系统跑起来之后，状态放在哪、靠什么驱动、误差怎么被消化、事实怎么记、怎么回放。

---

## 一、运行时模型

### 1.1 两层状态

| 层 | 性质 | 内容 |
| --- | --- | --- |
| **逻辑真理层** | 无状态，唯一的真相来源 | 一切长期为真的东西：账目、知识、已完成的观测。全部在存储里 |
| **任务会话层** | 有状态，但可重建 | 每个（玛丽 × 本次运行）的工作记忆：已下达的子目标、在等谁的回话、已发起未见效的方法调用 |

**会话层不是第二处真相。** 它的内容就是存储中"已下达、未比对"记录在内存里的投影。进程崩了，拿这些记录重放，会话原地重建。

这条性质的实际价值：**毁掉一个运行中的实例没有任何损失。**

### 1.2 实例化是懒惰的

组装只确定"用哪些组件、怎么连"，不创建会话。会话在子目标**实际下达**时才创建。所以一张很大的图，如果只有一条分支被真正触发，其余部分零成本。

### 1.3 一次运行的边界

**一次运行的终点 = 所有预测已比对。** 预测跨运行到期就没有人对它负责对账，所以运行不能提前结束；预测全部比对完之后，没有任何未了结的事，图可以散。运行时长因此由预测的观察期决定，不由节拍数决定（见 00 §五）。运行结束后，树/森林/图解散，下次从最新知识重新组装。

## 二、驱动：节拍与心跳

系统有两种驱动方式，职责不同。

| | 业务节拍 | 心跳巡视 |
| --- | --- | --- |
| **触发** | 新观测到达、或时间到点 | 独立的定时器，与业务事件无关 |
| **问的问题** | "发生了什么，要不要纠偏" | "**什么都没发生，但本该发生**吗" |
| **典型发现** | 误差超容差、需要行动 | 预测到期未观测、数据源静默、会话超时 |
| **节拍频率** | 可按指标分档 | 独立于一 |

**心跳是必要的，因为"没发生"不会自己产生事件。** 没有心跳，一个断掉的数据源和一个正常平静的指标，在账目上看起来一样。

心跳自身只在产出报告时才入账，没产出报告就不留痕。这样做是为了避免账目被无信息的定时记录淹没。但心跳发现的"该发生的事没发生"是事实，**发现的结论要入账**。

## 三、运行循环

每个节拍上，每个活跃的玛丽运行同一个循环。它的形状来自预测加工：**预测 → 观测 → 误差 → 修正**。

```
PREDICT   读当前的预测（上次生成时冻结的预期变化 / 知识条目）
OBSERVE   读入观测                          → 观测事件 / 环境事件
COMPARE   现算误差（观测 × 预测的预期），不落库
DECIDE    ① 误差超出容差带了吗？            → 没超：继续观测，不动作
          ② 本层有可用的方法吗？            → 没有：报告缺口，停下等人
          ③ 有方法：选择它
ACT       执行方法 + 生成预测（预期 + 观察期）→ 预测事件
          执行体是人时另记执行事件              → 已派发 / 已确认 / 已完成 / 前提未成立
BOOKKEEP  落账 + 按级别报告                  → 报告事件（记"报告了这件事"，不记误差本身）
```

三点说明：

- **玛丽只做一件事：选择方法并执行。** 这条在哪个场景都一样。执行体是人（等于向人提建议）、是机器、还是外部接口，由方法定义里的执行体字段承载——**那是知识，不是架构**。所以运行时没有"提议"与"执行"两条通路，只有一条；
- **前置的两问与授权无关**：容差带定目标精度，方法库定能力。授权只限定范围——她能看到哪些知识、能做哪些操作；看不到、做不到的东西对她不存在；
- 三件事各自独立，不要合成一个"预算"。

### 3.1 什么情况下自行处置，什么情况下报告

判据是**有没有手段**，与误差大小无关：

| 情形 | 系统行为 |
|---|---|
| 误差在容差带内 | 继续观测，不动作、不报告 |
| 超出容差带，有可用方法 | 选择并执行它，入账，进报告层 |
| 超出容差带，没有任何可用方法 | 报告**方法缺口**，停下等人 |
| 拆不动（没有拆解知识，或只有粗粒度描述） | 报告**知识缺口** |
| 需要观测的指标拿不到数据 | 报告**数据缺口** |
| 资源被多个目标争夺且解不开 | 报告**结构缺口** |

原则：**报告的永远是"我缺什么"，不是"误差有多大"**。误差大不大只决定要不要动作，缺不缺东西才决定要不要找人。

执行体这一层差异不进这张表：方法定义成"向人建议"时，执行动作本身就是"提出这条建议"，记录里留下的是"已派发"，观测等下一次回流。对外表现是系统在等人，但对架构来说那只是一次普通的方法执行。

### 3.2 报告的目的

这是整套机制里最容易做错的一处，先把目的写清楚。三个层次各司其职：

| 层次 | 目的 | 谁消费 | 覆盖范围 |
|---|---|---|---|
| **入账** | 留下可回放的事实 | 机器（回放、审计、分析） | 全部：观测、执行、误差、预测，一条不漏 |
| **报告** | 让人知道有什么变化 | 人（看，不必马上动） | **全部执行结果与误差**，按级别决定推不推送 |
| **上报** | 请人做一件只有人能做的事 | 人（必须动） | 只含系统自己走不下去的条目 |

**上报的目的是请求一个动作，不是传递一个数字。** 人能做的、系统替不了的动作只有这些：补知识、补方法、接数据、改规则、做取舍、担风险、发起尝试。一条上报如果指不出要人做其中哪一件，它就不该出现在上报里。

### 3.3 报告分类

| 类型 | 要人做什么 | 时机 |
|---|---|---|
| **缺口** | 补知识 / 补方法 / 接数据 | 立即——系统没有别的通路 |
| **预测失准** | 修订知识：这版预期可能错了 | 尽快，异步 |
| **异常** | 处置（数据源静默、预测到期未观测、会话超时） | 尽快 |

三类都进报告层，全部执行结果也进报告层，按级别决定推不推送（见 §3.4）。注意**这里没有"方案待批"这一类**：在需要人签字的场景里，"申请批准"本身就是一个方法，执行体是那个签字的人——它走的是普通执行通路，不是一条单独的批准机制。

**预测失准与误差大小是两把尺子。** 一个方法每次都贴着预期下限、次次都在容差带内，系统会一直不说话——可二十次之后，这版预期已经明显偏了，继续按它做事会持续吃亏。这不是误差大，是预测偏。所以它的触发条件是"某方法的历史实际效果系统性偏离预期且样本量够"，与单次误差是否出带无关。它的目的是修订知识，属于异步事务，不需要打断人。

> 与 A 的关系：**没权限的东西玛丽根本看不到**，包括可执行的方法。所以"有方法但没授权"不是一种状态——在她那里，那个方法不存在。她只能报"我的视野里没有招"，缺口四类全部在她的可见范围内定义。

### 3.4 报告级别

全部执行结果与误差都进报告层，但不是每一条都要人立即介入：

| 级别 | 含义 | 通知方式 |
|---|---|---|
| 立即 | 系统停在这里等人 | 主动推送 |
| 尽快 | 有后续动作，但会持续吃亏 | 主动推送，可批量 |
| 备查 | 供了解与回看 | 只入账、只进列表，不推送 |

### 3.5 误差越大，动作越保守

观测与预测严重不符，说明当前知识在这个局面下不可靠。用不可靠的知识下重注，是恶性循环的开始。所以误差超量时反着来：

- 缩小干预幅度（降增益）；
- 只使用有实测记录的方法；
- 拉长观察期。

### 3.6 执行事件：区分"没执行"和"没效果"

执行体常常是人。人会拖延、会敷衍、会记错。因此每次方法执行都要记录执行过程：**已派发 / 已确认 / 已完成 / 前提未成立**。

"前提未成立"指方法压根没被执行。这时**结果不可观测，这次预测无从验证**——不必为它单开一套机制，它是预测的一种终态。没有这条记录，"方法不灵"和"压根没执行"在账目里无法区分，复盘会把执行问题误诊为知识问题。这是最容易被忽视、代价又最大的一类误诊。

人类的执行噪声不做特殊处理：它会自然沉淀进预期的宽度与均值里。账目保持诚实，系统不假设执行是完美的。

## 四、正常运转与两种情形

### 4.1 正常运转

所有指标都在容差带内、没有异常时，系统**继续观测、继续记账、继续进报告层，但不主动推送**。目标已经达成时系统不停机，也不该继续占用注意力——账照记、证据照存，使用方哪天想回头看，一切都在。

"别烦我"是合法的使用模式：容差带可以拉宽、确认级别可以提高。系统不因此"失职"，它只是把发言权交还给使用方。核心度量是**命中率**：推送出去的报告里，最终引发真实动作的比例。报告数量、响应时长都不算数。

### 4.2 两种情形

| | 常规运行 | 异常情形 |
| --- | --- | --- |
| **条件** | 全部指标在容差带内，无未比对的预测 | 指标突破容差带，或心跳发现异常 |
| **推送** | 不推送（仍入账、仍进列表） | 按级别推送 |
| **退出条件** | — | 异常被处置 |

## 五、记录与回放

### 5.1 只存两类东西

| 对象 | 性质 | 内容 |
| --- | --- | --- |
| **事件** | 不可变、只追加 | 发生了什么。核心字段只含通用词汇，场景细节全部挂在负载里 |
| **快照** | 周期性锚点 | 某一时刻相关指标的全量值 |

任意时刻的完整状态 = **最近快照 + 按序重放其后的事件**。快照频率是纯性能参数，不影响表达能力。

### 5.2 三条红线

1. **事件只追加、永不可改。** 记错了就追加一条更正事件，不许改旧记录；
2. **误差不落库。** 记录层只存事实——观测值、以及生成预测时冻结的预期。"误差"永远是这两者的**投影计算**，不作为事实存储；
3. **内核里不出现场景词汇。** 场景细节挂在事件负载里，因此新场景永不需要给事件表加列。

### 5.3 投影：从记录现算出来的视图

| 投影 | 算法 | 用途 |
| --- | --- | --- |
| **误差** | 观测 × 生成预测时冻结的预期 | 对账 |
| **审计链** | 沿因果父指针向上遍历至最初的目标 | 回答"当时为什么这么选" |
| **方法账目** | 按方法聚合执行事件与观测序列（次数、平均效果、样本量） | 方法选择与预测失准检测 |

**误差不落库的直接好处**：知识修正后"历史账目怎么办"不构成问题——换版本重跑投影即可，原始记录不动。代价是查询变重（快照 + 重放 + 遍历），这与"记录高频、分析离线偶尔"的实际负载特征相符。

### 5.4 回放必须幂等

**这是全套设计里最容易在实现中走样的一条。**

> **只有"追加事件"是允许的副作用。** 重放事件流的过程必须只读。

任何对外部世界产生影响的效果——通知使用方、调用外部接口、请求模型——都必须满足其一：

- 先写成事件，由事件流的消费者去执行（重放时不重复执行）；
- 或带唯一标识做幂等执行。

配套两条：生成预测时即冻结预期（重放时不重新推导）；投影算法带版本号（算法升级会让历史数字变化，这件事必须显式可查，不能装作不存在）。

### 5.5 知识变更怎么生效

| 对象 | 用哪个版本 |
| --- | --- |
| 未比对的预测 | 生成时绑定的版本，不追溯 |
| 本次运行的其余部分 | 组装时绑定的版本（图是静态的） |
| **下一次运行** | **重新组装，自动使用最新版本** |

**所以不需要"知识更新如何迁移到正在运行的图"这种机制——图每次运行都是新的。** 这就是"一次运行一张图、用完即散"换来的一致性。

### 5.6 归因后置

记录时不替任何动作圈定结果。动作的效果归属是**事后从完整序列里分析**的问题，不是记录时刻的问题。

原因很实际：一次动作之后，同期还发生了天气变化、竞对动作、其他动作的叠加。如果在观测的那一刻就回答"这个动作带来了多少效果"，答案一定是被污染的，而且污染会被封进一个数字里，事后再也拆不开。

于是同一份记录之上有三层分工：

| 层 | 问的问题 | 急不急 |
| --- | --- | --- |
| **记录层** | 发生了什么（完整时间线，含环境事件） | — |
| **簿记层** | 答应的事做到了吗、出带了吗 | 等不得（断供当天就要报警） |
| **分析层** | 这个动作对世界起了什么作用 | 急不得（事后从序列里算） |

**环境事件与自身动作记在同一条时间线上**，这是事后分析能够排除干扰的前提。要诚实地说它没解决什么：混淆不会消失，只是从"数据被污染"变成"分析有难度"——而后者是可以持续进步的。

## 六、系统的自我治理

系统自身也有需要盯的东西：知识供给的质量、观测数据的质量、各种管道是否正常。这些同样可以用玛丽来管——因为判断标准是一样的：**有可量化的目标、有可挑的方法、有异常要管。**

### 6.1 管道与玛丽是上下两层

任何功能的执行永远是代码。**配一个管理玛丽，指的是它头上多一个管理者**，不把功能本身改造成玛丽。

常态下这些管理玛丽没有会话、零运行成本——它们是沉睡的守夜人，异常时才醒来。付出的成本是一次性的定义工作，换回的是账目、误差报告、缺口上报全部复用同一套范式，不需要为每个功能单独写监控。

### 6.2 两条边界

1. **基岩不可玛丽化**（取舍见 D23）。用来报告故障的机制，不能靠它自己报告自己的故障。系统必须保留一块最原始的部分：进程退出码、外部守护重启、独立于系统自身总线与存储的告警通道。没有这块机制，系统就存在"坏了且永远没人知道"的死法。唯一的规则是：**基岩的依赖集合与被监视对象不相交**；
2. **资源硬约束。** 极端高频、极低延迟的路径上，连异常时激发的记账开销都负担不起的部分，退回纯代码加原始告警。

### 6.3 不为对称而玛丽化

找不出有意义的指标和方法的功能（例如纯展示），硬套玛丽是形式主义。
