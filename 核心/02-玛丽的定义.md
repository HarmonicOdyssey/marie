# 02 · 玛丽的定义

> 本篇回答：玛丽这个原子实体到底是什么、长什么样、怎么被定义、靠什么复用、她自己不负责什么。

---

## 一、一句话定义

**一个玛丽 = 负责一个输出指标的组件。**

她知道的只有四件事：我负责什么指标、我依赖什么指标、我有哪些可用的方法、我的账目在哪里。除此之外她什么都没有——没有记忆、没有意志、没有用户痕迹。

她做的只有三件事：

1. **往下传子目标**（带容差带）；
2. **往上传观测与误差**；
3. **在本地执行拆解逻辑、选择方法、记账对账**。

她不做因果推断，不为知识的正确性负责，不替任何人拍板。

---

## 二、M · Motivated：为什么存在、如何生长

这一个字母回答两个方向的问题。

### 2.1 运行时：被激发才存在

没有目标就没有玛丽。目标到达时她被实例化，目标结束（一次运行结束）时她随之消失。**没被激活的玛丽不消耗任何资源**——所以池子可以任意大，这是一个运行时特性，不是优化技巧。

### 2.2 构建时：被盘点而复用

新目标到来时，系统先做一次**盘点**：把目标展开成"需要哪些指标的玛丽"这份清单，拿去和池子比对。

- 池子里有的 → **直接复用**；
- 池子里没有的 → **缺口**，带着位置被记录下来。

于是每次组装都产出两份东西：

| 产物 | 用途 |
| --- | --- |
| 服务本次目标的组件图 | 本次运行 |
| 池子的缺口清单 | 池子生长的方向标 |

### 2.3 三条推论

1. **服务新目标会越来越便宜**：第一个目标可能要新建大部分组件，池子变厚之后越来越接近"全部现成、直接组装"；
2. **覆盖率是可量化的健康指标**：新目标能复用多少现有玛丽，直接度量系统对这一类业务的覆盖程度；
3. **复用率是最重要的实测数字**。它同时也是组件颗粒度是否合适的唯一校准手段——见 §六。

---

## 三、A · Authorizable：为谁服务、看到哪个世界

### 3.1 授权加在数据上，不加在组件上

玛丽的输入指标、输出指标是恒定的——**她的职责不变**。变化的是她能读到存储的哪一部分。

同一个"客流玛丽"：

| 服务对象 | 她看到的 |
| --- | --- |
| 总部 | 全部门店的方法与汇总账目 |
| 某一家门店 | 该店授权的方法与账目 |
| 无人设备场景中的某台设备 | 该设备相关的遥测与可用动作 |

**授权只有一个作用面：存储里的数据内容。** 方法定义、历史账目、观测数据都在同一套存储里，因此不存在"数据可读 / 方法可用 / 历史可见"这类分层粒度——它们是同一件事的三个说法。授权决定她能看到哪些内容，而她**看得到什么，就等于她能用什么**：看不到的方法在她那里不存在，看不到的历史她无法据以评估方法。

一条推论：**她能调用什么、能拿什么做依据，都不需要单独授权。** 因为那些东西本来就只存在于她有权限看到的那部分数据里。

### 3.2 三个后果

1. **玛丽是可复用的角色模板**：定义一次，服务 N 个对象。池子是共享基础设施，每个对象的私有状态全部留在存储里，玛丽身上不留任何痕迹，天然无交叉污染；
2. **信息不对称从成本变成功能**：不同对象看到不同的世界切片，是授权的副产品，不需要单独实现；
3. **多世界叠加视图**：通用知识放在共享世界，各对象的账目与私有内容放在各自的世界，玛丽按授权把多个世界叠加起来看。

---

## 四、R · Repository-based：状态在哪里

### 4.1 玛丽不持有长期状态

她身上没有"她记住的东西"，只有"她被允许读到的东西"。实现上可以有任何内存缓存，**但缓存必须能随时丢弃并从存储重建**。

### 4.2 行为 = 组件 × 世界

这是全套架构里最有用的一条式子。同一个玛丽定义，插上不同的世界视图，就得到不同的行为：

| 插上什么世界 | 得到什么 |
| --- | --- |
| 当前世界 | 正常运营 |
| 历史版本的世界 | 回放审计（"当时为什么这么决策"） |
| 模拟数据的世界 | 沙盘演练 |
| 只有声明、没有实测的世界 | 冷启动状态 |

这几件看起来无关的事，做的是同一件事：**给同一个玛丽换世界**。

### 4.3 两条进化线解耦

| 进化线 | 变化时的影响 |
| --- | --- |
| 知识与账目的积累 | 不需要改动玛丽定义 |
| 玛丽逻辑的升级 | 不需要迁移历史数据 |

## 五、I · Inference：干什么活

### 5.1 三类活动

| 活动 | 输入 | 输出 |
| --- | --- | --- |
| 拆解 | 一个带容差带的子目标 | 拆给各输入指标的子目标 |
| 观测与误差上报 | 观测值 | 与预期的误差，超出容差才上报 |
| 方法选择与执行 | 候选方法及其历史账目 | 一条**预测**（预期什么、何时看结果） |

### 5.2 两条纪律

- **不做因果推断。** 她只说"知识说这个方法带 10~20%，实际 11%，在区间内"。为什么、要不要改知识，是人的事；
- **下层不拒绝、不协商。** 收到子目标就执行拆解并返回观测与误差；做不到就报缺口，不许静默、不许猜。

### 5.3 方法选择看什么

排序的输入项是固定的：适用条件、预期、历史误差、成本、情态强度、使用方偏好。**排序规则是知识**——调整规则走知识修改流程，不改代码。

一个方法的效果是**多维的**，不区分"主效果"和"副作用"。副作用只是记账时没预料到的效果维度，补全它靠复盘。同理，"预算不超支"是一个目标，超支就是那个目标上的误差，走相同的对账通道。

## 六、E · Entity：怎么被组装（以及颗粒度）

### 6.1 可命名、可引用、可组合

玛丽以**指标**为锚点被引用。指标是稳定的词汇表，任务是易变的句子：

> **用稳定的词汇表，服务易变的句子。**

这是复用能够成立的根本原因。如果玛丽以任务命名（"筹备年会""做一次促销"），复用立刻失效，因为任务几乎不重复。

### 6.2 颗粒度是这套架构最容易做错的地方

| 颗粒度 | 后果 |
| --- | --- |
| 太粗（一个玛丽管一整个目标） | 复用率低，池子长不厚，每次组装都要新建 |
| 太细（一个玛丽管一个算术运算） | 组件数量爆炸，组装与维护成本反超收益 |

**颗粒度的校准方式只有一种：实测复用率。** 目标形态是——第一个场景新建大部分组件，第二个场景开始出现可观复用，第三个场景复用率继续上升。如果三个场景的复用率都接近零，说明颗粒度错了，此时该停下来改颗粒度，不要再加功能。

衡量单位是**指标**而非代码行数：一个玛丽负责一个输出指标，输入指标是她的依赖面。

## 七、玛丽的定义

```typescript
interface MarieDefinition {
  key: string;                          // 稳定标识
  version: Version;                     // 定义自身可迭代
  output_indicator: IndicatorRef;       // 她负责的指标（唯一）
  input_indicators: IndicatorRef[];     // 她依赖的指标
  decomposition: DecompositionBinding;  // 怎么把目标摊到输入上
  methods: MethodRef[];                 // 可用方法（引用知识条目）
  gaps: GapPolicy;                      // 拆不动 / 无方法时怎么报
}

// 拆解逻辑的绑定：内容在知识里，这里只存引用与版本
type DecompositionBinding = {
  entry: string;        // 知识条目 key
  version: Version;     // 绑定时的版本（预测与回放都靠它）
};
```

两条约定：

- **定义里不许出现场景词汇。** `output_indicator` 是 `IndicatorRef`，不是"客流"；场景词汇只存在于指标元数据与配置里；
- **定义不带实现细节。** 她是编译成代码执行、还是每次由语言模型解释，是实现绑定的事，不是定义的事。

**方法的执行体是知识，不是架构。** 方法定义里带一个执行体字段（人 / 机器 / 外部接口）。企业场景里方法多被定义成"向某人提出建议"，执行体是人，所以系统看起来总在提建议；游戏场景里方法就是操作本身，执行体是机器，系统就直接操作了。对玛丽来说两者是同一个动作——**选择一个方法并执行**。架构不为执行体的差异保留分支。

## 八、玛丽做不到的四件事（缺口分类）

系统做不到的地方必须显式上报，且**指出位置**。与玛丽直接相关的四类：

| 缺口 | 含义 | 例子 |
| --- | --- | --- |
| **数据缺口** | 指标既不可观测，也无法再分解 | "这个指标没有数据源" |
| **知识缺口** | 拆解逻辑缺失，或只有无法执行的粗粒度描述 | "不知道怎么拆" |
| **方法缺口** | 某环节没有任何可行方法 | "没有招可用" |
| **组件缺口** | 组装时发现这个位置缺一个玛丽 | 缺口最精确的形态，也是池子生长的方向标 |

（另有一类**结构缺口**，指资源冲突无解，属于组装层，见 04。）

**上报之后**：使用方的回答进入原文层、建立锚点，下次同类目标不再上报。在无人场景中，缺口由场景指定的外部流程处理——这是场景绑定要定义的内容，见 07。

---

## 九、玛丽不负责什么

| 不负责 | 归属 |
| --- | --- |
| 拆解逻辑的正确性 | 知识供给方 |
| 因果推断、归因 | 事后的分析（人，或场景指定的分析流程） |
| 修改自己的逻辑源 | 知识修改流程（在无人场景中由场景绑定规定） |
| 替人拍板 | 使用方 |
| 主动发起探索性尝试 | 使用方 |
| 结果兜底 | 使用方 |
