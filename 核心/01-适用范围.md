# 01 · 适用范围

> 本篇回答：什么样的场景归这套架构管，为什么这三条条件是充分的，以及什么明确不归它管。

---

## 一、三个条件

| # | 条件 | 判定方式 |
| --- | --- | --- |
| C1 | **目标可量化** | 能否写出目标值、容差带、期限。目标可以是向量（多个指标同时成立），并可为某些维度设红线 |
| C2 | **环境有可量化指标** | 目标本身是否是这些指标之一，或能否拆解到这些指标上。拆到的每一个末端指标都必须有观测来源 |
| C3 | **持续运营** | 系统是否长期运行。"长期"的判定是：一次运行结束、图解散之后，还会因为同一个或新的目标再次组装 |

三条同时满足才适用。任一条不满足时，先把它变成满足，或者换一套架构。

**判定用的一句话**：能不能写出"目标 → 指标 → 方法 → 观测"这条链？写不出来就是还没想清楚，那是**知识缺口**，不是场景不适用。

---

## 二、为什么 C2 是充分的

### 2.1 观测本来就只取一部分

人类和机器观测现实世界，拿到的是**其中一部分指标，而不是世界的全貌**。感知是选择性的，仪表是有量程的，台账是有栏目的。用文字记录现实世界，是对这些指标的又一次精简提炼。

所以：

> **自然语言本身就是对现实世界的一次量化与压缩。**

推论：把现实世界的记录输入任何现代图灵机系统，输入**必然是已成指标的东西**。"现实世界太复杂、无法量化"这个说法，描述的是观测的选择性，不是系统的能力边界。

### 2.2 "定性描述"是什么

一句"交付周期受设计、采购、施工影响，具体权重看情况"，它仍是指标，只是：

- **粒度更粗**（没有给出权重，但给出了依赖关系）；
- **边界更模糊**（"看情况"意味着条件未穷举）。

所以要问的是两个可测的问题：

| 问题 | 怎么测 |
| --- | --- |
| **粒度够不够细** | 这段原文提炼出的指标，能不能支撑逐节拍的对账？还是只能支撑"看趋势"？ |
| **稳不稳定** | 同样的输入条件下，从这段原文得出的判断是否一致？重复执行是否漂移？ |

粒度粗、稳定性差的条目，处理方式是**降低它的对账精度**（只报突变与趋势反转），不把它排除在架构之外。

### 2.3 由此得到的一条纪律

**任何目标、方法效果、观测都必须落到指标上。** 说不清指标就报缺口，不猜、不用含糊描述填充。这条纪律的作用是把"不知道"变成有地址的、可被补齐的东西。

## 三、C3：逼近，不结项

### 3.1 两类场景，同一套机制

| 目标形态 | 例子 | 系统行为 |
| --- | --- | --- |
| **可达** | 某个物理量维持在设定值附近 | 进入容差带 → 正常运转 |
| **不可达** | 组织运营：问题总会出现，目标永远在更远处 | 持续解决新出现的问题，误差曲线长期压在带内 |

两类场景走的是同一套机制：**预测 → 观测 → 误差 → 修正**。误差在哪一层被处理掉，取决于那一层有没有手段（见 05 §三），与误差大小无关。区别只在"达标"这个状态是否存在——而**系统不依赖它是否存在**。

### 3.2 由此产生的四条设计后果

1. **收敛判据是曲线，不是状态**：看误差随时间的走势是否被压在容差带内并保持稳定，不看某一天是否达标；
2. **需要"正常运转"这种姿态**：目标已在带内时系统不停机、也不继续打扰人——它继续观测记账，但不主动推送，突破即唤醒；
3. **报告的触发条件是缺口**：报告的永远是"我缺什么"，不是"误差有多大"。误差大不大只决定要不要动作，缺不缺东西才决定要不要找人；
4. **系统永不进入"完成"**：一次运行会结束、图会解散，但运营继续。**"结束"是运行的结束，不是系统的结束。**

### 3.3 一个诚实的边界

真正**未被已有知识覆盖的局面**，任何系统都无法在当下正确应对。系统在这里如实记录失败：每一层的预测、观测、误差各是多少。这次失败因此成为下一次知识更新的原料，不成为被掩盖的事故。

## 四、领域无关性

### 4.1 架构本体 vs 应用示例

| | 内容 | 是否属于架构本体 |
| --- | --- | --- |
| 原子实体（MARIE）的定义方式 | 以指标定义、无长期状态、局部推理 | ✅ 本体 |
| 存储的两层结构 | 原文层 + 知识层 | ✅ 本体（既定设计） |
| 逼近循环 | 预测加工、报告分层、正常运转 | ✅ 本体 |
| 树 / 森林 / 图 | 三种组装形态 | ✅ 本体 |
| 咖啡店、策略游戏、矿山调度、项目管理…… | 具体场景的拆解逻辑、方法、指标 | ❌ 应用层 |

**纪律**：文档和代码里不许把应用层的词汇当成架构概念。"门店""客流""战力""里程碑"只能出现在配置与知识里，不能出现在内核里。

### 4.2 领域无关性怎么被检验

判定靠三个可测的事实，不靠声明：

1. **同一批原子实体能否装出树、森林、图三种形态**——且不新增内核概念；
2. **换场景时内核代码改动是否为零**——由机器判定，人不必争论；
3. **玛丽与存储之间是否只有一层薄接口**——换掉存储实现，玛丽行为是否不变。

## 五、什么不归这套架构管

| 不属于 | 原因 |
| --- | --- |
| **一次性的规划求解** | C3 不满足。有成熟求解器，且不需要持续记账 |
| **无法给出任何量化目标的场景** | C1 不满足。此时该先想清楚目标，而不是先上系统 |
| **纯展示、纯检索类功能** | 没有可量化的目标要逼近，也没有异常要管 |
| **因果推断与预测未来** | 架构明确不做。预测的职责由知识承担（人写的、历史攒的、外部推演的），系统只逐时刻对账 |
| **探索性尝试** | 是否要试一条没数据的新路，是经营者的判断，不由系统发起。系统只报告"这里没有数据、把握低" |
| **替人拍板** | 系统提供证据、候选与误差，判断权在人（或场景指定的外部流程） |

## 六、责任划分

| 系统负责 | 使用方负责 |
| --- | --- |
| 按给定逻辑拆解、算账、追踪、执行、报告误差 | 拆解逻辑与业务模型的**内容与正确性** |
| 记录误差、报告，然后等待 | 复盘、修正知识 |
| 提供证据与候选 | 拍板，并对结果负责 |

三条推论：

1. **没有永远正确的模型。** 系统可以忠实执行一份有缺陷的拆解并得到有缺陷的结果。它的职责是让误差尽快可见，不是弥补知识；
2. **系统不知道怎么拆，等于使用方还没搞清楚拆解逻辑。** 报缺口，等人来填；
3. **系统不做因果推断，只做簿记。** 下结论永远是人的动作。

---

## 七、天花板

**系统放大已有的认知，不创造认知。**

| 场景类型 | 天花板由什么决定 |
| --- | --- |
| 企业 / 组织 | 使用方的管理认知水平，以及复盘是否真的发生 |
| 配置驱动类（如游戏策划） | 配置的质量与覆盖度 |
| 模型驱动类（如训练管线） | 管线的样本效率与目标函数设计 |
| 无人设备类 | 观测接口的完备性 |

这条天花的含义是：**系统的价值随知识供给的质量单调上升**。它不会因为上了系统就变聪明，但会因为知识被持续沉淀而越来越省力。
